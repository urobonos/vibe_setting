# Task Docs Skill

작업 문서 3종(analyze, plan, result)을 `docs/tasks/YYYYMMDD/` 디렉토리에 표준 템플릿으로 생성·관리한다.
소프트웨어 개발 산출물 4종(SDP, SRS, SDD, IDD)을 `docs/output/specs/` 디렉토리에 표준 템플릿으로 생성·관리한다.

## 공통 규칙

1. **날짜별·작업별 누적 보관한다** — 기존 파일을 덮어쓰지 않는다. 새 작업마다 새 서브디렉토리를 생성한다.
2. **보고용 문서 산출물:** 사용자 요청 보고서는 `docs/output/`에 생성. `docs/tasks/`와 혼용하지 않는다.
3. `{작업명}`은 작업 내용을 간결하게 표현하는 kebab-case 이름으로 한다 (예: `pay-refactor`, `callee-migration`).
4. `YYYYMMDD`는 작업 시작일 기준이다 (예: `20260324`).
5. 사용자에게 보고하는 동시에 파일에도 동일 내용을 기록한다. 채팅으로만 보고하고 파일 생성을 누락하는 것은 지침 위반이다.
6. **팀 간 산출물 체이닝 필수:** Team 2는 반드시 `analyze.md`를 Read한 뒤 기반으로 plan을 작성한다. Team 3는 반드시 `plan.md`를 Read한 뒤 기반으로 실행한다. 이전 팀 산출물 파일이 없으면 해당 팀에 진입할 수 없다.
7. **체크리스트 최대 생성 원칙:** 모든 문서(analyze, plan, result)에 검증 가능한 체크리스트(`- [ ]`)를 최대한 생성한다. 분석 항목, 작업 단계, 검증 조건, 보안 점검, 테스트 케이스 등 체크박스로 표현 가능한 항목은 전부 체크리스트로 작성한다. 서술형 나열보다 체크리스트를 우선한다.

## 파일 경로

```
docs/tasks/YYYYMMDD/{작업명}/
  {작업명}-analyze.md     ← Team 1 (Analyze) 분석 결과
  {작업명}-plan.md        ← Team 2 (Plan) 실행 계획 + Blueprint
  {작업명}-result.md      ← Team 3 (Execute) 완료 결과
```

# Part 4. Context Persistence 연동

컨텍스트 압축이 임박할 때, 작업 문서(analyze.md, plan.md, result.md)가 **진행 상황 복원의 핵심 매체** 역할을 한다.

- **즉시 기록 원칙:** 각 팀 산출물은 팀 완료 즉시 파일에 기록한다. 메인 컨텍스트에만 보관하고 파일 생성을 미루지 않는다.
- **복원 시 활용:** 컨텍스트 압축 후 재개 시, 메모리에 저장된 "현재 단계 + 산출물 경로"를 읽고, 해당 파일을 Read하여 작업을 이어간다.

# Part 5. 소프트웨어 개발 산출물 (docs/output/specs/)

소프트웨어 개발 산출물 4종(SDP, SRS, SDD, IDD)을 `docs/output/specs/` 단일 디렉토리에 플랫하게 관리한다.

## 공통 규칙

1. **단일 디렉토리:** 모든 산출물은 `docs/output/specs/`에 저장한다. 문서 타입별 하위 폴더를 만들지 않는다.
2. **파일 네이밍:** `{모듈 또는 주제}-{문서타입}.md` (kebab-case)
   - 예: `auth-srs.md`, `commerce-idd.md`, `project-sdp.md`
   - 프로젝트 전체 문서는 `project-` 접두사를 사용한다.
   - 모듈별 문서는 BC명(kebab-case)을 접두사로 사용한다.
3. **Glob 패턴으로 타입별 조회 가능:** `specs/*-srs.md`, `specs/*-sdd.md` 등
4. **기존 파일 덮어쓰기 허용:** specs 문서는 요구사항·설계 변경 시 갱신한다. (tasks 문서와 다름)
5. **버전 관리:** 문서 상단 `version`과 `lastUpdated` 필드로 변경 이력을 추적한다.

## 문서 4종 개요

| 타입 | 정식 명칭 | 작성 시점 | 범위 |
|------|----------|----------|------|
| **SDP** | Software Development Plan | 프로젝트 착수 / 마일스톤 시작 | 프로젝트 전체 (1회성) |
| **SRS** | Software Requirements Specification | 모듈 개발 전 | 모듈(BC)별 또는 기능별 |
| **SDD** | Software Design Document | 설계 확정 시 | 모듈(BC)별 |
| **IDD** | Interface Design Document | API/모듈 간 통신 설계 시 | 모듈(BC)별 또는 시스템 간 |

## 5-3. SDD — Software Design Document

모듈(BC)별 시스템 아키텍처, 클래스 설계, DB 설계를 정의한다.

### 파일 경로
```
docs/output/specs/{모듈}-sdd.md
예: auth-sdd.md, commerce-sdd.md
```

### 템플릿

```markdown
# {모듈명} — Software Design Document
> version: 1.0 | lastUpdated: YYYY-MM-DD | module: {BC명}

## 1. 설계 개요
| 항목 | 내용 |
|------|------|
| 모듈(BC) | {BC명} |
| 아키텍처 패턴 | {Modular Monolith — Layered} |
| 기반 SRS | `{모듈}-srs.md` v{버전} |

## 2. 디렉토리 구조
```text
app/Modules/{BC}/
├── Controllers/
├── Services/
├── Repositories/
├── Models/
├── Entities/
└── Config/
    └── Routes.php
```

## 3. 클래스 설계

### 3-1. Controller Layer
| 클래스 | 메서드 | HTTP | URL | 설명 |
|--------|--------|------|-----|------|
| `{Controller}` | `index()` | GET | `/{url}` | {설명} |

### 3-2. Service Layer
| 클래스 | 메서드 | 입력 | 출력 | 설명 |
|--------|--------|------|------|------|
| `{Service}` | `{method}()` | {DTO/파라미터} | {반환타입} | {설명} |

### 3-3. Repository Layer
| 클래스 | 메서드 | 쿼리 유형 | 설명 |
|--------|--------|----------|------|
| `{Repository}` | `{method}()` | {SELECT/INSERT/...} | {설명} |

## 4. Entity / VO
| 클래스 | 타입 | 속성 | 설명 |
|--------|------|------|------|
| `{Entity}` | Entity | {속성 목록} | {설명} |

## 5. DB 설계

### 5-1. 테이블 정의
| 테이블 | 설명 | 주요 컬럼 |
|--------|------|----------|
| `{table}` | {설명} | {컬럼 목록} |

```text

|--------|---------|------|------|------|

## 6. 시퀀스 (주요 흐름)
```text

## 트리거 조건

다음 상황에서 해당 문서 생성/갱신을 안내한다.

| 트리거 | 생성 문서 |
|--------|----------|
| 프로젝트 착수 / 마일스톤 시작 | SDP |
| 모듈(BC) 신규 개발 착수 | SRS → SDD → IDD (순차) |
| 요구사항 변경 | SRS 갱신 |
| 설계 변경 | SDD 갱신 → IDD 동기화 확인 |
| 외부 연동 추가 | IDD 갱신 |
| 사용자 명시 요청 (`/task-docs specs`) | 지정 문서 생성 |
