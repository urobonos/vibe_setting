## 1. 개요

### 1-1. 목적

글로벌 화면설계서 검수리스트 23번 항목에 따라, 사용자 접속 시 서비스 노출 기준(IP/회원 국가코드)에 대한 **사용자 제안 3-Case 모델**이 제시되었다.

본 문서는 해당 모델을 기획검수안 §7(REG-001~REG-014-2, 14건)과 §8(App vs Web 시나리오 비교)에 대해 **동조 없이 객관적으로 교차 검증**하여, 미정의·충돌·불완전 영역을 갭 시나리오로 도출한다.

### 1-2. V2.0 핵심 변경점

| 항목 | v1.0 | v2.0 |
|------|------|------|
| 리전 전환 정의 | 3가지 해석 병존 (GAP-7) | **확정**: 언어팩 + 데이터 전체 변경 |
| GAP-7 상태 | High (미정의) | **Resolved** |
| 심각도 변경 | — | GAP-9 Medium→High, GAP-10 Medium→High |
| 신규 GAP | — | **GAP-11** 리전 전환 시 개인 데이터 경계 미정의 |
| 갭 총 건수 | 10건 (활성 10) | **11건** (활성 10, 해소 1) |
| 분석 기반 | 정책 문서만 | **as-is 시스템 구조** + 정책 문서 (KR/JP 코드베이스 전수분석 반영) |

### 1-3. 검토 범위

- **입력**: 사용자 3-Case 모델 + 확정 전제 조건(리전 전환 = 전체 전환)
- **비교 기준**: `플랫폼_노출_IP_기준_시나리오.md` §7(14건 REG 매핑) + §8(App/Web 6개 시나리오 그룹)
- **추가 분석 기반**: hongcafe-korea(`hongcafe3`), hongcafe-japan 코드베이스 전수분석, `API_FIELD_MAP.md`, 도메인별 FFS/QSS
- **출력**: 갭 11건 + 심각도 분류 + 데이터 경계 정책 + 결정 필요 사항

## 2. 확정 전제 조건 — 리전 전환 = 전체 전환

### 2-1. 전제 정의

> **리전 전환 시 언어팩과 서비스 데이터가 동시에 변경된다. 언어팩만 변경되거나 데이터만 변경되는 시나리오는 통합 프로젝트에 존재하지 않는다.**

이는 기획검수안 §3-5의 3가지 해석 중 **(B) 리전 전체 전환**에 해당한다.

| 해석 | 내용 | 채택 여부 |
|------|------|-----------|
| (A) UI 표시 언어만 변경 | 텍스트만 번역, 콘텐츠·통화·상품은 원래 리전 유지 | **배제** |
| **(B) 서비스 리전 전체 전환** | **콘텐츠·통화·상품·UI 모두 대상 리전으로 변경** | **확정** |
| (C) hostname 이동만 | 브라우저 URL만 변경, 데이터 동기화 미보장 | **배제** |

### 2-2. 리전별 서비스 데이터 비교 — as-is 시스템 기반

현재 KR(`hongcafe3`)과 JP(`hongcafe-japan`)는 **별도 코드베이스·별도 운영**이다. 통합 프로젝트는 이를 최초로 단일 시스템에서 처리한다. 리전 전환 시 변경되는 데이터의 범위를 as-is 분석 기반으로 정리한다.

| 데이터 유형 | KR (hongcafe.com) | JP (jp.hongcafe.com) | EN (en.hongcafe.com) |
|------------|-------------------|---------------------|---------------------|
| **상담사 풀** | KR 등록 상담사 | JP 등록 상담사 | EN 등록 상담사 |
| **통화** | KRW (원) | JPY (円) | USD ($) |
| **코인 가격** | `it_coin_price` (KRW 기준) | `it_coin_price` (JPY 기준) | `it_coin_price` (USD 기준) |
| **결제수단** | NicePay, KakaoPay, NaverPay, TossPay, Mcash, PayLetter, PayPal **(7종)** | Stripe **(1종)** | TBD |
| **SNS 로그인** | Kakao, Naver, Apple, Google, Line, Facebook | Google, Apple, Line, Facebook | TBD |
| **본인인증** | ICERTSecu (공인인증 CI/DI) | SMS OTP | TBD |
| **메인 탭** | 전화상담, 채팅상담, 클래스, 홍카페홍대, 대면상담, 서비스상품 **(6개)** | 전화상담, 채팅상담 **(2개)** | 전화상담, 채팅상담 **(2개)** |
| **전용 기능** | Ambassador, Partnership(3-tier MLM), PGMainBase, Green, Cafe, Campaign, ThemeBanner, Applink, Hongmentor 등 **(12종)** | 없음 | 없음 |
| **부가세** | 10% (`pd_price × 1.1`) | Stripe 자동 처리 | 없음 |
| **카테고리 구성** | 전체, 영감영시, 타로, 사주성명, 이벤트, 후기 + KR 전용 | 상이 (기획 확정 필요) | 상이 (기획 확정 필요) |

> **핵심**: 리전 전환은 UI 텍스트 번역이 아니라, **사실상 완전히 다른 서비스로 이동**하는 것과 동일하다.

### 2-3. 전제 조건의 아키텍처 영향

| 영향 영역 | 내용 |
|----------|------|
| **hostname의 역할** | hostname = 서비스 리전의 물리적 구현체. `jp.hongcafe.com` 접속 = JP 서비스 전체 데이터 수신 |
| **API 컨텍스트** | 리전 전환 = 모든 API 호출의 `country_code` 파라미터 변경. 상담사 목록, 코인 가격, 결제수단 등 전면 교체 |
| **세션 관리** | 리전 전환 시 기존 세션의 서비스 컨텍스트(장바구니, 진행 중 상담 등) 처리 방안 필요 |
| **캐시 전략** | CDN·브라우저 캐시가 이전 리전 데이터를 보유할 가능성. 전환 시 캐시 무효화 필요 |

### 2-4. 전제에 대한 객관적 검토 — 전체 전환이 야기하는 신규 문제

전체 전환 전제는 명확한 방향을 제시하지만, 동시에 v1.0에서 다루지 않은 문제를 발생시킨다.

**문제 1. 교차 리전 개인 데이터 처리**

현재 KR/JP는 별도 시스템이다. 통합 프로젝트에서 한 사용자가 리전을 전환하면:
- JPY로 구매한 코인 잔액 → EN(USD) 서비스에서 표시 가능? 사용 가능?
- JP 상담사와의 상담 이력 → EN 서비스에서 조회 가능?
- JP 상담사를 즐겨찾기한 목록 → EN 서비스에서 표시?

"서비스 데이터 전체 변경"의 "전체"가 서비스 카탈로그(상담사, 가격 등)만 의미하는지, 개인 데이터(코인, 이력 등)까지 포함하는지 미정의. → **GAP-11로 도출**

**문제 2. 기능 비대칭**

KR은 12개 전용 기능(Ambassador, Partnership 등)이 있다. JP/EN 사용자가 KR로 전환하면 이 기능이 노출되는가? 역으로 KR 사용자가 JP로 전환하면 사라지는가? 기능 가용성이 회원 국가에 종속되는지, 현재 리전에 종속되는지 미정의.

**문제 3. 인증 호환**

KR은 ICERTSecu(공인인증 CI/DI)를 사용한다. JP 사용자가 KR로 전환 시, CI/DI가 없으므로 ICERTSecu 의존 기능(실명인증, 환불 등)을 사용할 수 없다. 리전 전환으로 인해 사용 불가 기능이 발생하는 경우의 처리 방안 미정의.

**문제 4. 결제 법적 관할**

JP 회원(일본 거주)이 KR 서비스로 전환하여 NicePay로 KRW 결제를 시도하면, 결제 법적 관할(소비자보호법, 환불 정책)은 어디 기준인가? 이는 서비스 이용약관과 직결된다.

## 3. 현황 분석 — 사용자 3-Case 모델

### 3-1. 원문

> **전제**: 사용자가 한국(`hongcafe.com`), 일본(`jp.hongcafe.com`), 미국(`en.hongcafe.com`) **어떤 도메인으로 접근하든** 아래 규칙을 적용한다.

| Case | 조건 | 노출 기준 |
|------|------|-----------|
| **Case 1** | 초기접근(비회원) | GeoIP 기준으로 사용자 국가 서비스 출력 |
| **Case 2** | 회원(로그인) | 회원 국가를 기준으로 서비스 출력 |
| **Case 3** | 회원(언어 변경 후 종료→재접속) | 종료 전 국가 서비스 상관없이 **회원 국가 기준**으로 서비스 출력 |

### 3-2. 전체 전환 전제 적용 시 재해석

전체 전환 전제가 확정됨에 따라, 각 Case의 의미가 구체화된다.

| Case | v1.0 해석 (언어 변경 정의 모호) | v2.0 해석 (전체 전환 확정) |
|------|------|------|
| **Case 1** | GeoIP → 해당 국가 서비스 표시 | GeoIP → 해당 국가의 **상담사·가격·결제수단·UI 전체** 표시 |
| **Case 2** | 회원 국가 기준 서비스 | 회원 국가의 **전체 서비스 데이터** 기본 노출, 타 리전 전환 시 대상 리전 **전체 데이터** 교체 |
| **Case 3** | "언어 변경" 후 재접속 시 회원 국가 복원 | **리전 전체 전환**(상담사·가격·결제수단 모두 변경) 후 재접속 시 회원 국가의 **전체 데이터**로 강제 복원 |

**Case 3에 대한 객관적 문제 제기**:

전체 전환이 확정된 상황에서 Case 3은 다음을 의미한다:

```
JP 회원이 EN 서비스로 전환
  → US 상담사 목록, USD 가격, Stripe 결제, 2개 탭 UI 사용 중
  → 앱 종료 후 재접속
  → Case 3에 의해 JP 서비스로 강제 복원
  → JP 상담사, JPY, Stripe, 2개 탭으로 전체 교체
```

이는 단순히 "UI 언어가 돌아가는" 수준이 아니라, **진행 중이던 서비스 컨텍스트 전체가 리셋**되는 것이다. EN 상담사와 상담 예약을 잡아둔 사용자가 재접속 시 JP로 강제 이동되면, 해당 예약을 찾을 수 없는 상황이 발생한다.

### 3-3. 모델의 구조적 한계 (v1.0 유지 + v2.0 추가)

| 한계 | 내용 | 영향 |
|------|------|------|
| 도메인 역할 미정의 | "어떤 도메인이든" → hostname 무시 전제 | 현 아키텍처와 충돌 (GAP-1) |
| 중간 상태 부재 | 비회원→회원 전환 과정 미정의 | 가입 시 국가 오배정 위험 (GAP-5) |
| 폴백 부재 | GeoIP 실패·제3국 IP 처리 없음 | 서비스 미노출 위험 (GAP-2, GAP-3) |
| 저장 전략 부재 | 캐시/쿠키/세션 우선순위 없음 | 재방문 UX 불일치 (GAP-9) |
| **[V2.0]** 전체 전환 시 Case 3 UX 문제 | 리전 전체 리셋의 영향이 언어 리셋보다 훨씬 큼 | 서비스 연속성 파괴 (GAP-6 심화) |
| **[V2.0]** 개인 데이터 경계 부재 | "전체 변경"의 범위(서비스 데이터만? 개인 데이터 포함?)가 미정의 | 데이터 모델 설계 차단 (GAP-11) |

### 4-2. 갭 상세

---

#### GAP-1. hostname(도메인) vs GeoIP 충돌 — Critical

> **유형**: 아키텍처 충돌
> **관련**: REG-014(딥링크 URL 리전 우선), REG-014-2(URL 리전 ≠ 회원 국가)
> **V2.0 변경**: 분석 강화 — 전체 전환 전제로 hostname의 아키텍처적 중요성 상승

| 구분 | 내용 |
|------|------|
| **사용자 모델** | "어떤 도메인이든" → 도메인은 노출 기준에서 제외, GeoIP만 사용 |
| **기획검수안 §7** | REG-014: 딥링크/캠페인 URL 리전 → **URL 리전 우선** + 전환 배너 |
| **기획검수안 §8-6** | `hongcafe.com/jp/event/123` → URL 리전 우선 노출 |

**충돌 시나리오** (전체 전환 전제 반영):

```
일본 사용자(GeoIP=JP)가 en.hongcafe.com에 직접 접속

  사용자 모델 → GeoIP(JP) 우선 → JP 상담사, JPY, Stripe, 2탭 전부 출력
  기획검수안  → URL 리전(EN) 우선 → EN 상담사, USD, TBD PG, 2탭 전부 출력
  → 상담사 풀, 통화, 결제수단이 정반대
```

**전체 전환 전제로 인한 영향 확대**:

v1.0에서는 "언어가 다르게 표시될 수 있다" 수준이었으나, v2.0에서는 **완전히 다른 상품 카탈로그가 노출**된다. `en.hongcafe.com`에서 GeoIP(JP)를 우선하여 JP 데이터를 보여주면:

1. URL(`en.hongcafe.com`)과 실제 콘텐츠(JP 상담사, JPY)가 불일치
2. SNS 공유 시 `en.hongcafe.com/counselor/123` 링크가 JP 데이터를 가리킴 — 수신자(EN 사용자)가 접근 시 또 다른 충돌
3. SEO 측면에서 `en.hongcafe.com`이 JP 콘텐츠를 인덱싱

**현재 구현 상태와의 괴리**:

현재 프로젝트는 **path-based 라우팅**(`/en/*`, `/ko/*`, `/ja/*`)을 사용 중이며, hostname-based 라우팅은 미구현이다. hostname-based로 전환하는 시점과 방법도 결정이 필요하다.

| 결정 필요 사항 |
|---|
| (A) hostname 무시 → 단일 도메인(`hongcafe.com`) + GeoIP 리다이렉트 구조 전환 |
| (B) hostname 유지 → 도메인 접속 = 사용자 의도 (GeoIP는 메인 도메인 접속 시에만) |
| (C) 혼합 → `hongcafe.com`(메인) 접속 시 GeoIP 적용 / 직접 도메인 접속 시 hostname 우선 |
| **[V2.0 추가]** (D) path-based → hostname-based 전환 시점 및 마이그레이션 계획 |

#### GAP-2. 제3국 IP 처리 — High

> **유형**: 정책 누락
> **관련**: REG-007(제3국 IP → 선택화면), REG-008(IP 판별 실패 폴백)
> **V2.0 변경**: 변동 없음

| 구분 | 내용 |
|------|------|
| **사용자 모델** | "GeoIP 기준 국가 서비스 출력" — 제3국 처리 없음 |
| **기획검수안 §7** | REG-007: KR/JP/US 외 제3국 IP → **선택화면(B안)** 권고 |

**시나리오**:

```
태국 사용자(GeoIP=TH)가 hongcafe.com 접속

  사용자 모델 → GeoIP(TH) 기준 → TH 서비스? (존재하지 않음)
  기획검수안  → 제3국 IP → 리전 선택화면 노출
```

**영향 범위**:
- 서비스 대상국은 KR/JP/US 3개국뿐이다. GeoIP가 이 3국 외를 반환하면 **매핑 불가**.
- 동남아 거주 일본인/한국인 사용자 비중을 고려하면, 제3국 IP는 무시할 수 없는 트래픽이다.
- 전체 전환 전제 하에서, 리전 선택화면은 "언어 선택"이 아닌 "어느 국가의 전체 서비스를 이용할 것인가"의 선택이 된다. 선택화면의 안내 문구가 이를 명확히 전달해야 한다.

| 결정 필요 사항 |
|---|
| (A) 제3국 IP → 리전 선택화면 (§7 REG-007 권고안) |
| (B) 제3국 IP → EN 서비스 기본 출력 (글로벌 기본값) |
| (C) 제3국 IP → KR 서비스 기본 출력 (본사 기준) |

#### GAP-3. GeoIP 실패·타임아웃 폴백 — Medium

> **유형**: 장애 대응 누락
> **관련**: REG-004-P(200ms 이내, 실패 시 즉시 폴백), REG-008(IP 판별 실패)
> **V2.0 변경**: 변동 없음 — 전체 전환 전제와 무관한 인프라 이슈

| 구분 | 내용 |
|------|------|
| **사용자 모델** | GeoIP가 항상 성공한다고 가정 (폴백 없음) |
| **기획검수안 §7** | REG-004-P: **200ms 이내**, 실패 시 즉시 폴백 |
| **기획검수안 §8-8** | SSR(Next.js) 서버사이드 IP 판별 → 깜빡임 방지 |

**장애 시나리오**:

| 상황 | GeoIP 결과 | 대응 |
|------|-----------|------|
| GeoIP API 서버 장애 | 응답 없음 | 폴백 필요 |
| GeoIP DB 미갱신 | 잘못된 국가 반환 | 오판별 → 전체 데이터 오류 |
| 프록시/CDN 내부 IP(10.x.x.x) | private range → 판별 불가 | 폴백 필요 |
| API 응답 > 200ms | 타임아웃 | 폴백 필요 |

**참고**: GAP-1에서 hostname 우선 전략(B 또는 C)이 채택되면, 특정 hostname 접속 시 GeoIP 실패의 영향이 축소된다. hostname 자체가 리전 정보를 포함하기 때문이다. GeoIP 실패가 실질적으로 영향을 미치는 경우는 `hongcafe.com`(메인 도메인) 접속 시뿐이다.

| 결정 필요 사항 |
|---|
| (A) 폴백 전략: KR 기본 / EN 기본 / 리전 선택화면 |
| (B) 지연 허용 한도: 200ms(§7 권고) 수용 여부 |
| (C) GeoIP DB 운영: 상용(MaxMind GeoLite2 등) vs Cloudflare `CF-IPCountry` 헤더, 갱신 주기 |

#### GAP-4. VPN 사용자 — Low

> **유형**: 예외 누락
> **관련**: REG-010(VPN 의심 시 선택화면), §8-2(App vs Web VPN 감지 차이)
> **V2.0 변경**: 영향 범위 약간 확대 — 잘못된 리전 배정 시 전체 데이터 오류

| 구분 | 내용 |
|------|------|
| **사용자 모델** | VPN 시나리오 없음 |
| **기획검수안 §7** | REG-010: VPN 의심 시 선택화면 |
| **기획검수안 §8-2** | Web: IP만으로 판별(시그널 제한적) / App: 디바이스 로케일+IP 교차검증 가능 |

**시나리오**:

```
한국 사용자가 미국 VPN 사용 → GeoIP=US

  사용자 모델 → US 서비스 출력 (US 상담사, USD, TBD PG — 한국어 서비스 아님)
  기획검수안  → IP+디바이스 교차검증 → 불일치 시 선택화면
```

전체 전환 전제 하에서, VPN으로 인한 오판별은 "단순히 영어 UI가 보이는" 수준이 아니라 **US 상담사, USD 가격이 노출**되는 것이다. 그러나 Web에서는 대응 수단이 구조적으로 제한된다.

**Web의 한계**: 브라우저에서는 디바이스 로케일, SIM 정보 등 부가 시그널을 얻을 수 없어 **IP만으로 판별**할 수밖에 없다. `Accept-Language` 헤더와 GeoIP를 교차검증하는 방법이 있으나, false positive가 빈번하다 (예: 영어 브라우저 사용 일본인).

**Low 유지 근거**: 로그인 후 회원 국가(Case 2)로 자동 전환되므로, VPN 영향은 비로그인 구간에 한정된다.

| 결정 필요 사항 |
|---|
| (A) Web: VPN IP 그대로 적용 (대응 불가 수용) |
| (B) Web: Accept-Language 헤더와 GeoIP 교차검증 → 불일치 시 선택화면 |
| (C) App 전용: 디바이스 로케일/SIM 국가와 교차검증 |

#### GAP-5. 가입 과정(비회원→회원 전환) — High

> **유형**: 전환 시나리오 누락
> **관련**: REG-011(해외 체류 가입 → 선택 국가코드 우선), REG-011-2(리전 선택 항상 허용), §8-3
> **V2.0 변경**: 영향 범위 대폭 확대 — 잘못된 국가 배정이 전체 서비스 데이터에 영향

| 구분 | 내용 |
|------|------|
| **사용자 모델** | Case 1(비회원) → Case 2(회원) 사이 전환 과정 없음 |
| **기획검수안 §7** | REG-011: 가입 시 선택 국가코드 우선 |
| **기획검수안 §7** | REG-011-2: IP ≠ 가입 희망 리전 → 리전 선택 항상 허용 + 휴대폰 국가 제안 |
| **기획검수안 §8-3** | Web: 리전 선택 드롭다운 + IP 기본값 / App: SIM 국가코드 기반 제안 |

**시나리오** (전체 전환 전제 반영):

```
일본인이 한국 출장 중 첫 가입

  GeoIP = KR → Case 1에 의해 KR 서비스(KR 상담사, KRW, NicePay 7종)에서 가입 진행
  → 가입 시 ac_country가 자동으로 KR로 배정
  → Case 2에 의해 이후 영구적으로 KR 전체 서비스 노출
  → 한국어 상담사, KRW 가격, NicePay 결제, ICERTSecu 인증 요구
  → 일본어를 사용하는 사용자가 한국어 전용 서비스에 잠김
```

**v2.0 영향 분석**:

v1.0에서는 "잘못된 국가 배정"이 언어 불일치 수준으로 다뤄졌으나, 전체 전환 전제 하에서는 다음이 추가로 발생한다:

| 오배정 결과 | JP 사용자 → KR 배정 시 |
|------------|----------------------|
| 상담사 | JP 상담사가 아닌 KR 상담사만 표시 → 일본어 상담 불가 |
| 결제 | Stripe가 아닌 NicePay 등 KR PG → 일본 발행 카드 사용 불가 가능 |
| 인증 | ICERTSecu 요구 기능 → JP 사용자는 한국 공인인증 불가 |
| 기능 | KR 전용 12종 기능 노출 → JP 사용자에게 무의미 |
| 통화 | JPY가 아닌 KRW 표시 → 가격 혼란 |

**as-is 시스템 참고**: 현재 KR 앱(`hongcafe3`)은 `CallConnect(it_code, 'KR')`, JP 앱(`hongcafe-japan`)은 `CallConnect(it_code, 'JP')`로 **country_code를 하드코딩**한다. 통합 프로젝트에서는 이를 동적으로 결정해야 하며, 가입 시 배정된 국가가 이 결정의 기본값이 된다.

**High 유지 근거**: 해결책(사용자 선택 + GeoIP 제안값)이 명확하고 구현이 단순하다. 다만, 미구현 시 영향이 **서비스 사용 불가 수준**이므로 구현 우선순위는 P0이다.

| 결정 필요 사항 |
|---|
| (A) GeoIP 기반 자동 배정 (오배정 위험) |
| (B) 사용자 선택 + GeoIP 제안값 (§7 REG-011-2 권고안) |
| (C) 전화번호 국가코드(+81, +1 등) 기반 자동 배정 |
| **[V2.0 추가]** (D) 가입 시 "이 국가 서비스의 상담사, 가격, 결제수단을 사용하게 됩니다" 명시적 안내 필수 |

#### GAP-6. Case 3 vs REG-013 직접 충돌 — Critical

> **유형**: 정책 충돌 (양립 불가)
> **관련**: REG-013(로그아웃 후 이전 선택 유지 + IP 충돌 시 선택화면)
> **V2.0 변경**: 전체 전환 전제로 충돌의 UX 영향이 대폭 심화

| 구분 | 내용 |
|------|------|
| **사용자 모델 Case 3** | 회원이 리전 전환 후 종료 → 재접속 시 **회원 국가 기준으로 강제 복원** (전환 무시) |
| **기획검수안 §7** | REG-013: 로그아웃 후 → **이전 선택 유지** + IP 충돌 시 선택화면 |

**충돌 시나리오** (전체 전환 전제 반영):

```
JP 회원이 EN 서비스로 전환 → 앱 종료 → 재접속

  Case 3   → JP 서비스 전체 복원 (JP 상담사, JPY, Stripe, 2탭)
  REG-013  → EN 서비스 유지 (EN 상담사, USD, TBD PG, 2탭)
  → 보고 있던 상담사 목록, 가격, 결제수단이 전부 바뀜 vs 유지됨
```

**v2.0 심화 분석 — 전체 전환이 Case 3에 미치는 영향**:

v1.0에서 Case 3은 "언어가 돌아가는" 정도로 해석될 여지가 있었다. 전체 전환이 확정된 v2.0에서는 Case 3이 다음을 의미한다:

| 상황 | Case 3 적용 시 (매 재접속마다 리셋) |
|------|------|
| EN 상담사와 예약 상담을 잡아둔 사용자 | 재접속 시 JP로 이동 → EN 상담사 예약 찾기 어려움 |
| USD 결제 장바구니에 코인 담아둔 사용자 | 재접속 시 JPY 장바구니로 전환? 또는 장바구니 초기화? |
| EN 상담사를 즐겨찾기한 사용자 | 재접속 시 JP에서 EN 즐겨찾기가 보이는가? |
| EN 서비스에서 후기를 작성 중이던 사용자 | 재접속 시 JP로 이동 → 임시 저장된 후기는? |

**UX 트레이드오프** (전체 전환 반영):

| 정책 | 장점 | 단점 |
|------|------|------|
| **Case 3 (회원 국가 강제 복원)** | 일관성 보장, 구현 단순, 개인 데이터 경계 문제 최소화 | 리전 전환이 사실상 무의미 — 매번 재설정 필요, 진행 중 작업 단절 |
| **REG-013 (이전 선택 유지)** | 사용자 선택 존중, 서비스 연속성 보장 | 교차 리전 개인 데이터 처리 복잡, 저장 매체 관리 필요, 로그아웃 시 혼란 가능 |

**객관적 판단**: 전체 전환 전제 하에서 Case 3의 "매번 리셋"은 **사용자 경험을 심각하게 저해**한다. 리전 전환 자체가 의도적 행위(상담사 풀, 가격 등을 다른 국가 것으로 보겠다는 결정)인데, 재접속할 때마다 이를 무시하면 리전 전환 기능의 존재 의의가 사라진다.

단, Case 3에도 합리적 근거가 있다: **개인 데이터 경계 문제(GAP-11)를 회피**할 수 있다. 매번 회원 국가로 복원하면, 교차 리전 데이터 처리 로직이 불필요하다.

| 결정 필요 사항 |
|---|
| (A) Case 3 채택 → 재접속 시 무조건 회원 국가 전체 복원 (REG-013 폐기) |
| (B) REG-013 채택 → 마지막 선택 리전 전체 데이터 유지 (Case 3 폐기) |
| (C) 혼합 → 로그인 유지 상태 재접속: 리전 유지 / 로그아웃 후 재접속: 회원 국가 복원 |
| **[V2.0 추가]** (D) 혼합(C) 채택 시, 진행 중 작업(예약, 장바구니) 처리 정책도 함께 결정 필요 |

> **유형**: ~~용어 모호~~ → **해소됨**
> **관련**: §3-5(수동 전환 범위), §8-5(저장 매체)

| 항목 | 결정 |

| GAP-1 | hostname = 전체 서비스 리전의 물리적 구현체로 역할 확정 |
| GAP-5 | 가입 시 국가 오배정의 영향이 전체 데이터 수준으로 확대 |
| GAP-6 | Case 3의 "리셋"이 전체 데이터 리셋을 의미 → UX 영향 심화 |
| GAP-9 | 캐시 오류 = 전체 데이터 오류 → 심각도 상향 |
| GAP-10 | 임시 전환(전체 데이터)과 영구 변경의 구분이 필수 |
| GAP-11 (신규) | "전체"의 범위(서비스 데이터만? 개인 데이터 포함?)가 신규 갭으로 도출 |

**미결 사항**: GAP-7 자체는 해소되었으나, 다음 2건은 별도 결정이 필요하다.

| 미결 항목 | 내용 |
|----------|------|
| 저장 매체 | httpOnly 쿠키 / 서버 DB / 세션 스토리지 |
| 유효 기간 | 세션(브라우저 닫으면 소멸) / N일 쿠키 / 서버 DB(영구) |

#### GAP-8. 비로그인 세션 중 IP 변경 — Low

> **유형**: 엣지케이스 누락
> **관련**: §3-8(네트워크 전환으로 IP 변경)
> **V2.0 변경**: 전체 전환 전제로 IP 재판별의 영향이 확대되나, 심각도는 Low 유지

| 구분 | 내용 |
|------|------|
| **사용자 모델** | 해당 시나리오 없음 |
| **기획검수안 §3-8** | WiFi↔모바일데이터, VPN ON/OFF로 IP 변경 → 리전 자동 갱신 여부 |

**시나리오** (전체 전환 반영):

```
비회원이 일본 WiFi(GeoIP=JP)로 접속 → JP 서비스 이용 중 (JP 상담사, JPY)
  → 모바일 데이터 전환(GeoIP=KR, 한국 로밍)
  → 매 요청 재판별 시: 갑자기 KR 서비스(KR 상담사, KRW)로 전체 전환
  → 보고 있던 상담사 프로필 페이지가 KR 데이터로 교체
```

전체 전환 전제 하에서, 세션 중 IP 변경에 의한 자동 리전 전환은 **매우 파괴적**이다. 첫 진입 시 IP를 고정하고 세션 내 일관성을 보장하는 것이 필수적이다.

**Low 유지 근거**: 비로그인 사용자 전용 엣지케이스이며, 첫 진입 IP 고정 + 쿠키 저장으로 해결 가능.

| 결정 필요 사항 |
|---|
| (A) 세션 중 IP 재판별 안 함 — 첫 진입 시 GeoIP 고정 (쿠키 저장) |
| (B) 매 페이지 이동마다 재판별 — UX 깜빡임 + 전체 데이터 교체 가능 |
| (C) SSR 레벨에서 첫 요청 IP 고정 + 쿠키 저장 — 세션 내 일관성 보장 |

#### GAP-9. 캐시·저장값 우선순위 — High ↑

> **유형**: 재방문 UX 누락
> **관련**: REG-013(이전 선택 유지), §3-9(저장값 vs IP 우선순위)
> **V2.0 변경**: Medium → **High** 상향. 캐시 오류 = 전체 서비스 데이터 오류

| 구분 | 내용 |
|------|------|
| **사용자 모델** | 저장값 개념 없음 — Case 1은 항상 GeoIP |
| **기획검수안 §7** | REG-013: 이전 선택 유지 + IP 충돌 시 선택화면 |
| **기획검수안 §3-9** | IP 우선 vs 저장값 우선, 저장값 유효 기간 |

**시나리오** (전체 전환 반영):

```
비회원이 첫 방문 시 JP 선택(쿠키 저장) → 한국 출장 → 재방문
  → IP는 KR, 쿠키는 JP

  사용자 모델 → GeoIP(KR) 우선
    → KR 상담사, KRW, NicePay 7종, ICERTSecu, 6탭 전체 출력
    → 이전에 보던 JP 상담사, JPY 등 전부 사라짐

  REG-013 → 쿠키(JP) ≠ IP(KR) 충돌 → 리전 선택화면
    → 사용자가 명시적으로 리전 선택 가능
```

**심각도 상향 근거**:

v1.0에서는 캐시 오류가 "잘못된 언어 표시" 수준이었으나, v2.0에서는 다음이 발생한다:

| 캐시 오류 결과 | 영향 |
|--------------|------|
| 상담사 풀 변경 | 이전에 열람하던 상담사가 전부 사라짐 |
| 통화 변경 | 가격이 KRW→JPY 또는 역방향으로 변경 → 혼란 |
| 결제수단 변경 | 이전에 사용하던 PG가 사라짐 |
| UI 구성 변경 | 탭 수 변경 (6개↔2개), 기능 가용성 변경 |

매 방문마다 GeoIP 재판별로 전체 데이터가 바뀌면, **비로그인 사용자의 서비스 일관성이 보장되지 않는다.** 해외 출장·여행이 빈번한 사용자일수록 영향이 크다.

| 결정 필요 사항 |
|---|
| (A) 비회원 재방문: 항상 GeoIP (저장값 무시, 매번 리전 변경 가능) |
| (B) 비회원 재방문: 저장값 우선 (만료 전까지) + IP 충돌 시 선택화면 |
| (C) 저장값 유효 기간: 세션 / 7일 / 30일 / 무기한 |

#### GAP-10. 회원 국가 변경 가능 여부 — High ↑

> **유형**: 정책 누락
> **관련**: §3-2(해외 회원의 한국 서비스 이용)
> **V2.0 변경**: Medium → **High** 상향. 임시 전환(전체 데이터)과 영구 변경의 구분이 필수화

| 구분 | 내용 |
|------|------|
| **사용자 모델 Case 2, 3** | "회원 국가 기준" — 회원 국가는 고정 전제 |
| **기획검수안 §3-2** | 해외 회원의 한국 서비스 이용 → 언어·플랫폼 전환 허용 범위 정책 필요 |

**전체 전환 전제에서 발생하는 이중 구조**:

전체 전환이 확정되면, 통합 프로젝트에는 두 가지 "국가" 개념이 공존한다:

| 개념 | 성격 | 변경 가능? | 결정 시점 | 영향 범위 |
|------|------|-----------|----------|----------|
| **회원 국가** (`ac_country`) | 영구적 소속. 결제·계약·법적 관할 결정 | 미정의 (GAP-10) | 가입 시 | 기본 서비스 리전, 결제 통화, 이용약관 |
| **현재 리전** | 임시 세션 설정. 현재 보는 서비스 결정 | 가능 (전체 전환) | 수시 | 상담사 풀, 가격 표시, UI 구성 |

**시나리오** (전체 전환 반영):

```
JP 회원(ac_country=JP)이 한국 콘텐츠(한국 상담사) 이용 희망

  Case 2 → JP 서비스만 기본 노출 (JP 상담사, JPY)
  전체 전환 → KR 리전으로 전환 가능 (KR 상담사, KRW, NicePay)
  → KR 서비스를 보는 것은 가능하지만, NicePay(KR PG)로 결제 가능?
  → ICERTSecu(KR 공인인증) 의존 기능은 사용 가능?
  → KR에서 코인 충전하면 JPY 잔액과 별개?
```

**영구 변경 시나리오**:

```
JP 회원이 한국으로 영구 이주 → ac_country를 KR로 변경 희망

  → 기존 JP 코인 잔액(JPY)은?
  → JP 상담사와의 상담 이력은?
  → JP에서 작성한 후기는?
  → 이용약관이 JP법→KR법으로 변경?
```

**심각도 상향 근거**: 전체 전환이 가능해지면, 사용자는 자연스럽게 "그냥 영구적으로 다른 국가 서비스를 사용하고 싶다"는 요구를 하게 된다. 이 요구에 대한 정책이 없으면 CS 대응이 불가하다.

| 결정 필요 사항 |
|---|
| (A) 회원 국가 변경 불가 — 임시 리전 전환만 허용 |
| (B) 회원 국가 변경 가능 — 마이페이지에서 KR/JP/US 전환 (기존 데이터 마이그레이션 필요) |
| (C) "회원 국가"와 "서비스 리전"을 분리 — 국가=JP(결제·법적) + 리전=KR(콘텐츠) 허용 |
| **[V2.0 추가]** (D) (C) 채택 시 결제 관할 규칙: 결제는 항상 회원 국가 PG 사용? 또는 현재 리전 PG 사용? |

#### GAP-11. 리전 전환 시 개인 데이터 경계 미정의 — High (신규)

> **유형**: 데이터 모델 누락
> **관련**: GAP-7 해소에서 파생 — "전체 변경"의 범위가 미정의
> **V2.0 신규**: 전체 전환 전제의 직접적 결과

**문제 정의**:

리전 전환 시 **서비스 데이터**(상담사 목록, 가격, 결제수단)가 전환 대상 리전으로 변경되는 것은 확정되었다. 그러나 **개인 데이터**의 처리 방식은 정의되지 않았다.

**개인 데이터 경계 매트릭스**:

| 개인 데이터 유형 | 리전 전환 시 동작 | 격리 or 공유? | 결정 필요 |
|----------------|-----------------|:----------:|:--------:|
| 보유 코인 잔액 | JPY 코인 → EN 서비스에서 사용 가능? | **미정** | ✅ |
| 코인 충전 이력 | JPY 결제 내역 → EN에서 조회? | **미정** | ✅ |
| 상담 이력 | JP 상담사와의 이력 → EN에서 조회? | **미정** | ✅ |
| 단골(즐겨찾기) | JP 상담사 즐겨찾기 → EN에서 표시? | **미정** | ✅ |
| 후기 | JP에서 작성한 후기 → EN에서 노출? | **미정** | ✅ |
| 알림 설정 | JP 상담사 접속 알림 → EN에서 수신? | **미정** | ✅ |
| 채팅 이력 | JP 채팅방 → EN에서 접근? | **미정** | ✅ |
| 프로필 정보 | 닉네임, 전화번호, 이메일 | 공유 (추정) | ⚠️ |
| 로그인 자격 증명 | JWT, 세션 | 공유 (필수) | — |

**설계 방향 2가지**:

**방향 A — 통합 모델 (Cross-region 공유)**:

```
하나의 사용자 계정 = 하나의 코인 잔액 + 하나의 이력
  → 리전 전환 시: 코인 잔액 통화 변환 표시, 모든 리전의 이력 통합 조회
  → 장점: 사용자 경험 단순, 데이터 일원화
  → 단점: 통화 변환 로직 필요, 교차 리전 상담사 표시 UX 복잡
```

**방향 B — 격리 모델 (Region-partitioned)**:

```
하나의 사용자 계정 = 리전별 독립 데이터 슬롯
  → JP 슬롯: JP 코인(JPY), JP 이력, JP 즐겨찾기
  → EN 슬롯: EN 코인(USD), EN 이력, EN 즐겨찾기
  → 리전 전환 시: 해당 리전 슬롯의 데이터만 표시
  → 장점: 데이터 경계 명확, 통화 혼동 없음
  → 단점: 사용자가 "내 데이터가 사라졌다"고 인식할 위험, 관리 복잡
```

**as-is 시스템 참고**: 현재 KR/JP는 **완전 격리**(별도 DB, 별도 코드베이스)이다. 동일 사용자가 KR과 JP에 각각 가입할 수도 있다(별도 계정). 통합 프로젝트에서 단일 계정으로 합치면, 격리 모델(B)이 기존 구조와 호환성이 높다. 통합 모델(A)은 백엔드 데이터 모델 전면 재설계를 요구한다.

**참고 사례**:
- **AWS**: 리전별 리소스 격리 (us-east-1의 EC2를 ap-northeast-1에서 볼 수 없음). 사용자 계정은 글로벌, 리소스는 리전별. (출처: AWS 공식 문서 "Regions and Availability Zones")
- **Shopify**: 국가별 스토어(Markets) 설정. 상품·가격·결제는 Market별 독립, 고객 계정은 글로벌. (출처: Shopify Help Center "Shopify Markets")
- **Apple App Store**: 국가/지역별 스토어. 구매 이력은 계정에 귀속되지만, 잔액·결제수단은 스토어(리전)별 격리. (출처: Apple Support "Change your Apple ID country or region")

| 결정 필요 사항 |
|---|
| (A) 통합 모델 — 단일 잔액(기준 통화), 전체 이력 통합 조회 |
| (B) 격리 모델 — 리전별 독립 데이터 슬롯, 전환 시 해당 슬롯만 표시 |
| (C) 혼합 모델 — 이력·즐겨찾기는 통합 조회, 코인·결제는 리전별 격리 |
| (D) 결정 전까지 임시 정책: 리전 전환 시 개인 데이터 섹션(마이메뉴)은 항상 회원 국가 기준 표시 |

(출처: Nielsen Norman Group "Persistence of User Preferences", W3C WCAG 3.2.2 On Input) |

| GAP | 권고안 | 근거 |
|-----|--------|------|
| **GAP-2** | **(A) 리전 선택화면** 채택 권고 | REG-007 권고안과 일치. EN 기본 출력 시 비영어권 제3국 사용자 이탈. 전체 전환 전제 하에서 선택화면은 "어느 국가의 상담사·가격을 보시겠습니까?"를 명확히 전달해야 한다. (출처: Airbnb 글로벌 서비스 — 미지원 리전 접속 시 언어·국가 선택 모달 표시) |
| **GAP-5** | **(B) 사용자 선택 + GeoIP 제안값** + **(D) 명시적 안내** 채택 권고 | REG-011-2와 일치. 전체 전환 전제 하에서 국가 오배정 = 전체 서비스 오류이므로, 가입 시 "이 국가를 선택하면 해당 국가의 상담사, 가격, 결제수단을 사용하게 됩니다"를 명시해야 한다. (출처: Apple App Store 가입 — 국가/지역 선택 필수 + IP 기반 제안값 표시) |
| **GAP-9** | **(B) 저장값 우선 + IP 충돌 시 선택화면** + 유효 기간 **30일** 권고 | 전체 전환 전제 하에서 매 방문 GeoIP 재판별은 전체 데이터 교체를 유발하여 UX 파괴적이다. httpOnly 쿠키로 마지막 선택 리전을 30일간 유지하고, IP 충돌 시에만 선택화면을 표시한다. (출처: MDN Web Docs "HTTP cookies — SameSite, Secure attributes") |
| **GAP-10** | **(C) "회원 국가"와 "서비스 리전" 분리** 권고 | 전체 전환이 가능한 시스템에서, 회원 국가(결제·법적 관할)와 서비스 리전(콘텐츠·UI)을 분리하면, JP 회원이 KR 서비스를 탐색하되 결제는 JP PG를 사용하는 구조가 가능하다. 단, 결제 관할 규칙(회원 국가 PG vs 현재 리전 PG)은 별도 결정 필요. (출처: Shopify Markets — 국가별 가격·결제 독립 설정, Apple App Store — 스토어 리전 변경 시 잔액 이전 불가) |
| **GAP-11** | **(C) 혼합 모델** 권고: 이력·즐겨찾기·알림은 통합 조회, 코인·결제는 리전별 격리 | as-is 시스템이 완전 격리(별도 DB)이므로, 코인·결제의 통합은 백엔드 전면 재설계가 필요하다. 이력·즐겨찾기는 조회만 하면 되므로 통합 조회가 상대적으로 단순하다. 코인·결제는 법적·회계적 이유로 리전별 격리가 안전하다. (출처: AWS "Regions and Availability Zones" — 리소스 격리 원칙, Apple Support "Change your Apple ID country or region" — 잔액 소진 후에만 리전 변경 허용) |

### 5-2. 사용자 3-Case → 8-Case 확장 권고안

위 갭 분석 + 전체 전환 전제를 반영하여, 사용자 3-Case 모델을 **8-Case로 확장**할 것을 권고한다.

| Case | 조건 | 노출 기준 | 근거 |
|------|------|-----------|------|
| **1-A** | 비회원 + KR/JP/US IP + 메인 도메인(`hongcafe.com`) 접속 | GeoIP 기준 → 해당 hostname 리다이렉트 → **전체 데이터** 출력 | REG-006, GAP-1(C) |
| **1-B** | 비회원 + 특정 도메인(`jp.hongcafe.com`) 직접 접속 | **hostname 우선** → JP **전체 데이터** 출력 (GeoIP 무시) | REG-014, GAP-1(C) |
| **1-C** | 비회원 + 제3국 IP 또는 GeoIP 실패 | **리전 선택화면** 표시 ("어느 국가 서비스를 이용하시겠습니까?") | REG-007, REG-008, GAP-2, GAP-3 |
| **2** | 회원(로그인) — 리전 전환 없음 | 회원 국가(`ac_country`) 기준 **전체 데이터** 출력 | REG-002 |
| **3-A** | 회원 + 리전 전환 + 로그인 유지 상태 재접속 | **마지막 선택 리전의 전체 데이터** 유지 | REG-013, GAP-6(C) |
| **3-B** | 회원 + 로그아웃 후 재접속 | **회원 국가 기준** 전체 데이터 복원 | Case 3 원안, GAP-6(C) |
| **4** | 가입 과정 (비회원→회원 전환) | 국가 선택 드롭다운 + GeoIP 제안값 + 전체 전환 안내 | REG-011-2, GAP-5 |
| **5** | 비회원 + 재방문 (쿠키 존재) + IP≠쿠키 | **리전 선택화면** 표시 (이전 선택 vs 현재 위치) | REG-013, GAP-9 |

### 5-3. 데이터 경계 정책 권고안

8-Case 모델과 별도로, 리전 전환 시 개인 데이터 처리를 정의하는 **데이터 경계 정책**이 필요하다.

| 데이터 유형 | 권고 정책 | 이유 |
|------------|----------|------|
| 상담사 목록·가격·결제수단 | **리전 전환 시 교체** | 서비스 데이터 — 전체 전환 전제 |
| SNS 로그인 옵션 | **리전 전환 시 교체** | 국가별 제공자 상이 |
| UI 탭·기능 구성 | **리전 전환 시 교체** | KR 전용 12종 등 |
| 코인 잔액 | **리전별 격리** 권고 | 통화 상이, 회계·법적 분리 필요 |
| 결제·충전 이력 | **리전별 격리** 권고 | 통화·PG 상이, 환불 관할 상이 |
| 상담 이력 | **통합 조회** 권고 | 조회 전용, 리전 불문 본인 이력 |
| 단골(즐겨찾기) | **통합 조회** 권고 | 리전 전환 후에도 이전 즐겨찾기 접근 필요 |
| 후기 | **통합 조회** 권고 | 작성 리전 표시 + 전체 조회 |
| 알림 설정 | **통합** 권고 | 리전 불문 상담사 알림 수신 |
| 프로필 정보 | **글로벌 공유** | 단일 계정 원칙 |
