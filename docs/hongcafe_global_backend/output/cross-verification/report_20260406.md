## 불일치 항목 상세 (정보망 근거 + 권고안)

### 불일치 1: API 응답 포맷 — `success` (boolean) vs `status` (string)

- **성민**: `{ "success": true, "data": {...} }` — boolean 타입
- **재영**: `{ "status": "success", "data": {...} }` — string 타입
- **정보망 근거**: REST API 베스트 프랙티스(2025-2026)는 HTTP 상태 코드만으로 성공/실패를 전달하고, 응답 본문에 중복 상태 필드를 넣지 않는 추세. 다만 프론트엔드 편의를 위해 포함하는 경우 boolean이 분기 로직에 더 적합.
  - [REST API Best Practices 2026 — Hevo](https://hevodata.com/learn/rest-api-best-practices/)
  - [Responses Best Practices — Speakeasy](https://www.speakeasy.com/api-design/responses)
- **권고**: `"success": true/false` (boolean) 방식 채택. `if (response.success)` 분기가 `if (response.status === 'success')` 대비 간결하고 타입 안전.

### 불일치 2: Repository 구현 방식 — Model extends vs 별도 클래스

- **성민**: Repository extends CI4 Model (`class CallRepository extends Model`)
- **재영**: Repository는 별도 클래스, model() 헬퍼로 CI4 Model 주입
- **정보망 근거**: CI4 공식 문서는 Entity 패턴에서 Repository를 Model과 분리하는 것을 권장. Repository Pattern 원칙에서 Repository는 데이터 저장 메커니즘에 대한 추상화이며, 특정 ORM/Model에 의존하지 않아야 테스트가 용이.
  - [CI4 Entity Classes Documentation](https://codeigniter4.github.io/userguide/models/entities.html)
  - [CI4 Repository Pattern Forum](https://forum.codeigniter.com/showthread.php?tid=81657)
- **권고**: 재영 방식(별도 클래스 + Model 주입) 채택 권고. 다만 단순 CRUD Repository는 Model extends 허용하는 예외 조항 검토.

### 불일치 3: 공유 모듈명 — Common vs Shared

- **성민**: `Modules/Common/` — 인증, 국가, 다국어 서비스
- **재영**: `Modules/Shared/` — Models, Entities, ValueObjects, Interfaces
- **정보망 근거**: DDD 기반 Modular Monolith에서 공유 코드는 무분별한 접근을 막아야 함. Kamil Grzybek의 참조 구현에서는 공유 커널(Shared Kernel)을 별도 프로젝트로 분리.
  - [Modular Monolith with DDD — Kamil Grzybek](https://github.com/kgrzybek/modular-monolith-with-ddd)
  - [Modular Monolith Primer](https://www.kamilgrzybek.com/blog/posts/modular-monolith-primer)
- **권고**: 두 모듈의 책임이 다르므로 **양쪽 모두 유지** 가능. `Common/` = 도메인 서비스(Auth, Country), `Shared/` = 공유 값 객체(Money, Email). 이름과 책임 범위를 명확히 정의하여 합의.

### 불일치 4: Controller 베이스 — BaseController vs ResourceController

- **성민**: `extends \App\Controllers\BaseController`
- **재영**: `extends ResourceController` (CI4 RESTful)
- **정보망 근거**: CI4 공식 문서에서 ResourceController는 RESTful CRUD에 특화된 보일러플레이트를 제공하며, `$format = 'json'` 자동 설정, `respond()`, `failNotFound()` 등 API 헬퍼 내장.
  - [CI4 RESTful Resource Handling](https://codeigniter4.github.io/userguide/incoming/restful.html)
  - [CI4 API Controller Guide](https://codeigniter.com/user_guide/guides/api/controller.html)
- **권고**: API 전용 컨트롤러에는 ResourceController 사용 권고. BaseController는 공통 필터/미들웨어용으로 유지. ResourceController가 BaseController를 내부적으로 extends하므로 양립 가능.

### 불일치 5: CSRF 방어 — SameSite + Custom Header vs CSRF Token

- **성민**: SameSite=Strict 쿠키(1차) + X-Requested-With 커스텀 헤더(2차)
- **재영**: 전통적 CSRF 토큰 보호
- **정보망 근거**: OWASP는 SameSite 쿠키만으로는 완전한 CSRF 방어가 안 되며 보조 수단으로 권장. 그러나 Same-Origin 아키텍처 + HttpOnly 쿠키 + Custom Header 조합은 CSRF를 효과적으로 방어. CSRF 토큰은 상태 관리 오버헤드 발생.
  - [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
  - [Do SameSite Cookies Solve CSRF — Medium](https://airman604.medium.com/do-samesite-cookies-solve-csrf-6dcd02dc9383)
- **권고**: Same-Origin 아키텍처에서는 성민 방식(SameSite + Custom Header) 채택 권고. CSRF 토큰보다 구현이 간결하고 상태 비저장.

### 불일치 6: 인증 토큰 저장 — HttpOnly 쿠키 전용 vs localStorage 허용

- **성민**: HttpOnly 쿠키 전용. localStorage/응답 body 토큰 노출 금지
- **재영**: cookie 또는 localStorage 허용
- **정보망 근거**: IETF draft-ietf-oauth-browser-based-apps-26(2025.12)는 브라우저 앱에서 토큰을 서버사이드로 관리(Token-Mediating Backend)를 권장. localStorage는 XSS 공격 시 전체 접근 가능.
  - [IETF Browser-Based Apps](https://datatracker.ietf.org/doc/draft-ietf-oauth-browser-based-apps/)
  - [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)
- **권고**: HttpOnly 쿠키 전용 방식 채택 권고. localStorage 토큰 저장은 보안 위험.

### 불일치 7: 테스트 디렉토리 구조

- **성민**: `tests/Unit/Modules/{ModuleName}/`
- **재영**: `tests/Modules/{BC}/Unit/` + `tests/Modules/{BC}/Feature/`
- **정보망 근거**: PHPUnit 공식 문서는 프로덕션 코드 구조를 미러링하는 것을 권장. 재영 방식은 모듈별로 Unit+Feature를 묶어 응집도가 높음.
  - [PHPUnit Organizing Tests](https://docs.phpunit.de/en/12.5/organizing-tests.html)
- **권고**: 합의 필요. 재영 방식이 모듈 독립성에 유리하나, 성민 방식은 CI4 기본 구조에 가까움.

### 불일치 8: 에러 코드명 차이

- **성민**: `VALIDATION_ERROR`
- **재영**: `VALIDATION_FAILED`
- **정보망 근거**: 업계 표준은 없으나, `_ERROR` suffix는 에러 유형 분류에, `_FAILED` suffix는 동작 결과 표현에 적합. 일관성이 핵심.
- **권고**: 에러 코드 네이밍 규칙 합의 필요. `{DOMAIN}_{ACTION_RESULT}` (예: VALIDATION_FAILED) 또는 `{DOMAIN}_{TYPE}` (예: VALIDATION_ERROR) 중 택일.

### 불일치 9: 페이지네이션 키명

- **성민**: `meta.page`
- **재영**: `meta.currentPage`
- **권고**: 합의 필요. `currentPage`가 의미 명확성에서 우수하나, `page`가 간결. 프론트엔드 편의 기준으로 결정.

### 불일치 10: Dual Mode (Legacy) 지원

- **성민**: Modular Monolith만 기재
- **재영**: Legacy 모드 + New 모드 이중 구조
- **권고**: 글로벌 신규 프로젝트에서 Legacy 코드 존재 여부에 따라 결정. 기존 USA 코드를 참조/수정할 가능성이 있다면 Dual Mode 개념 채택 권고.

### 불일치 11: 커밋 메시지 형식 — 성민 내부 불일치

- **성민 BE 11**: `[ModuleName] type: 설명` (대괄호)
- **성민 common-standards §14**: `type(scope): 제목` (Conventional Commits)
- **재영**: 미기재
- **권고**: common-standards §14가 최신(2026-04-03 개정)이므로 Conventional Commits 형식으로 통일. BE 11 대괄호 형식 폐기 필요.

### 불일치 12: PSR-4 네임스페이스 등록 방식

- **성민**: 단일 루트 매핑 (`App\ => app/`)으로 자동 해석
- **재영**: BC별 개별 등록 (`App\Modules\Order => APPPATH . 'Modules/Order'`)
- **정보망 근거**: PSR-4 표준에서 단일 루트 매핑이면 하위 네임스페이스 자동 해석. 개별 등록은 불필요한 중복이지만 명시성 제공.
  - [PSR-4 Autoloader — PHP-FIG](https://www.php-fig.org/psr/psr-4/)
- **권고**: CI4는 `App\` 단일 루트로 `app/` 하위 전체를 자동 해석하므로 개별 등록 불필요. 성민 방식(단일 루트) 권고.

### 불일치 13: New 모드 산출물 수

- **성민**: 7개 (Controller, Service+IF, Repository, Entities, Interfaces, Routes, Services)
- **재영**: 9개 (7개 + Model + API 명세서 md+yaml)
- **권고**: Model 분리(불일치 5)와 API 명세서(불일치 8)는 별도 항목으로 합의 후 결정.

### 불일치 14: MySQL ANSI SQL 병기 의무

- **성민**: 미기재
- **재영**: MySQL 전용 구문 사용 시 ANSI 대안 병기 필수
- **정보망 근거**: DB 포터빌리티는 프로젝트 요건에 따라 결정. Aurora MySQL 고정 프로젝트에서 ANSI 병기는 오버헤드.
  - [MySQL Standards Compliance](https://dev.mysql.com/doc/refman/8.0/en/compatibility.html)
- **권고**: Aurora MySQL 고정이므로 ANSI 병기 의무는 과도. 단, CTE/Window Function 등 표준 SQL인 구문은 병기 불필요, 순수 MySQL 전용 함수(IFNULL, GROUP_CONCAT)만 주석으로 ANSI 대안 표기 권고.
