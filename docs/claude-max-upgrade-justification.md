## 2. Max 5 플랜의 구조적 한계

### 2.1 Rate Limit 병목

Max 5는 Pro 대비 5배 한도를 제공하나, 현재 사용 패턴은 이를 초과하는 구간이 반복적으로 발생한다.

- **일평균 Opus 소비:** 594,125 tokens/일 (활동일 기준)
- **피크일 Opus 소비:** 1,529,128 tokens/일 (일평균의 **2.6배**)
- **피크 구간 빈도:** 월 4~6일 (대규모 리팩토링 · 아키텍처 작업일)

한도 도달 시 **세션 중단 → 대기 → 재개**의 비효율이 발생하며, 이는 단순히 "기다리면 되는" 문제가 아니라 **컨텍스트 손실**로 이어진다.

### 2.2 Multi-Agent Orchestration 토큰 증폭

현재 운용 중인 자동화 체계가 세션당 토큰 소비를 구조적으로 증폭시킨다:

| 자동화 계층 | 구성 | 토큰 영향 |
|------------|------|----------|
| **Hook 시스템** | 21개 (PreToolUse 7, PostToolUse 7, Stop 3, 기타 4) | 매 Tool Call마다 Hook 실행 → 추가 컨텍스트 소비 |
| **Gate 워크플로우** | Analyze(gate≥1) → Plan(gate≥2) → Execute(gate≥3) | 3단계 강제 순회 → 단순 작업도 최소 3회 교환 |
| **스킬 시스템** | 51개 스킬 파일 (11 코어 + 40 플러그인) | 스킬 로드 시 컨텍스트에 삽입 |
| **메모리 시스템** | 30개 파일 (4개 프로젝트) | 세션 초기화 시 관련 메모리 로드 |
| **모니터링** | 134개 세션 리포트 + 122개 스냅샷 | 세션 종료 시 리포트 생성 |

이 체계는 **코드 품질 보장에 필수적**이나, 동시에 토큰 소비를 단순 대화 대비 **3~5배 증폭**시킨다. Hook을 줄여 토큰을 아끼는 것은 품질 보장 체계를 해체하는 것이므로 대안이 될 수 없다.

### 2.3 컨텍스트 손실의 실질적 비용

Rate limit 도달로 세션이 중단될 때 발생하는 비용:

1. **상태 복원 오버헤드:** Gate 워크플로우 상태(Analyze→Plan 중간 지점), 편집 중인 파일 컨텍스트, 진행 중인 멀티파일 리팩토링 상태를 새 세션에서 재구성해야 함
2. **중복 토큰 소비:** 중단된 세션의 컨텍스트를 새 세션에서 다시 읽어야 하므로, 한도 절약이 아닌 **한도 낭비**가 발생
3. **작업 일관성 저하:** 471개 파일에 `declare(strict_types=1)` 적용, 29개 DI 리팩토링 같은 대규모 작업에서 세션 단절은 누락 · 불일치 위험을 키움

## 5. 사용 패턴 기반 예측

### 5.1 향후 사용량 증가 요인

1. **글로벌 서비스 확장:** hongcafe_global 프로젝트가 다국가 서비스로 확대 예정 → 다국어 · 다지역 코드 복잡도 증가
2. **CI/CD 고도화:** Bitbucket Pipeline + AWS 연동 자동화 → 인프라 작업 빈도 증가
3. **보안 감사 정례화:** security-audit 스킬 기반 정기 점검 → 추가 세션 소비
4. **팀 에이전트 활성화:** 현재 비활동 상태인 2개 팀(default, payment-system) 재가동 시 토큰 소비 급증

### 5.2 Max 20 적정성 검증

| 지표 | Max 5 한도 | 현재 사용량 | Max 20 한도 | 여유율 |
|------|-----------|-----------|-----------|--------|
| Pro 대비 배수 | 5x | ~4.2x (평일) / ~8x (피크) | 20x | 충분 |
| Opus 일일 여유 | 빈번히 초과 | 피크 1.5M tokens/일 | 여유 확보 | 안정적 |

## 6. 결론 및 요청사항

### 업그레이드가 필요한 3가지 핵심 이유

1. **현재 사용량이 이미 Max 5 한도를 초과하는 구간이 월 4~6일 발생** — 업무일의 20~30%에서 생산성 저하가 발생하고 있음
2. **Multi-Agent 거버넌스 체계(21 Hooks + Gate 시스템)가 토큰을 구조적으로 증폭** — 이 체계는 코드 품질 보장에 필수이므로 축소 불가
3. **4개 프로젝트 동시 운용 + 향후 서비스 확장**으로 사용량은 감소가 아닌 증가 추세

### 요청

- **Max 5 → Max 20 플랜 전환** 승인 요청
- 전환 시점: **즉시** (현재 피크 구간 진입 중)
- 예상 효과: 월 10~16시간 생산시간 회수, 대규모 작업 시 세션 연속성 보장
