# 회원가입 플로우 설계 분석 보고서

> **작성일:** 2026-04-16
> **목적:** 회원가입 CAPTCHA 배치(분리형 vs 통합형)에 대한 업계 표준·법적 요건·공식 권장사항 비교 분석, CAPTCHA 만료로 인한 UX 저하 문제 분석 및 개선안 도출

---

## 1. 배경

### 1.1 서비스 인증 플로우

현재 서비스의 회원가입 인증은 두 단계뿐이다.

1. **CAPTCHA 인증** — 로봇 필터
2. **휴대폰 SMS 인증** — 본인 확인

CAPTCHA 도입 목적은 **SMS 무차별 발송 방지**다. 봇이 SMS 발송 API를 반복 호출하는 것을 차단한다.

### 1.2 현행 문제

CAPTCHA 토큰 유효시간이 약 30초로 극히 짧다. 2안(통합형) 구조에서 SMS 발송 후 인증번호 입력까지의 시간이 토큰 유효시간을 초과하여, 정상 사용자가 CAPTCHA 만료 오류를 경험한다.

---

## 2. 검토 대상 안

### 2.1 1안 — CAPTCHA 분리형 (3페이지)

```
페이지1: CAPTCHA 로봇 필터
  └─ CAPTCHA 클릭 → 서버가 세션에 인증 완료 저장 → 페이지2로 이동

페이지2: 회원정보 입력 + SMS 인증
  └─ 휴대폰 번호 입력 → SMS 발송 → 인증번호 입력 (세션 기반, CAPTCHA 토큰 불필요)

페이지3: 가입 완료
```

**특징:** CAPTCHA를 별도 페이지에서 완결하고 세션에 인증 상태를 저장한 뒤 다음 페이지로 이동한다. SMS 인증 시점에 CAPTCHA 토큰을 참조하지 않으므로 **만료 문제가 구조적으로 발생하지 않는다.**

### 2.2 2안 — CAPTCHA 통합형 (2페이지)

```
페이지1: 회원정보 입력 + CAPTCHA + SMS 인증
  └─ CAPTCHA 클릭 → 휴대폰 번호 입력 → SMS 발송 → (대기) → 인증번호 입력
                                                      ↑
                                               이 사이에 CAPTCHA 만료

페이지2: 가입 완료
```

**특징:** 한 페이지에서 CAPTCHA와 SMS 인증을 모두 처리한다. CAPTCHA 토큰이 SMS 발송~인증번호 입력 구간까지 유효해야 하는데, 30초 유효시간으로는 **거의 확정적으로 만료**된다.

## 3. 1안 vs 2안 비교 분석

| 항목 | 1안 (CAPTCHA 분리) | 2안 (CAPTCHA 통합) |
|------|-------------------|-------------------|
| **페이지 수** | 3 | 2 |
| **CAPTCHA 만료 문제** | **발생하지 않음** (세션 저장 후 이동) | **발생함** (발송~인증 사이 만료) |
| **CAPTCHA 소비 방식** | 페이지1에서 1회 소비 → 세션 저장 | 페이지1 내에서 토큰 유지 필요 |
| **UX — 인증 실패** | 없음 | 반복 루프 (재인증→재발송→재입력) |
| **UX — 페이지 전환** | 추가 1스텝 | 없음 |
| **봇 차단 시점** | SMS 발송 전 선차단 | 제출 시점 차단 |
| **업계 일반 채택률** | 소수 | 다수 |

### 3.1 핵심 차이

일반적인 회원가입에서는 2안이 UX상 유리하다. 그러나 **현재 서비스처럼 CAPTCHA → SMS 인증이 순차적으로 연결되고, CAPTCHA 유효시간이 30초인 환경**에서는 상황이 역전된다.

- **2안의 문제:** CAPTCHA 토큰이 SMS 전체 플로우(발송 대기 + 수신 + 입력)를 커버해야 한다. 30초로는 불가능.
- **1안의 장점:** CAPTCHA를 먼저 완결하고 세션에 저장하므로, SMS 인증과 CAPTCHA의 생명주기가 완전히 분리된다.

### 3.2 이탈률 관점

| 시나리오 | 1안 | 2안 |
|---------|-----|-----|
| CAPTCHA 페이지 추가에 의한 이탈 | 약간 존재 | 없음 |
| CAPTCHA 만료 재시도에 의한 이탈 | 없음 | **심각** |
| **종합 이탈 위험** | 낮음 | 높음 |

페이지가 하나 더 있는 것보다, 인증 실패가 반복되는 것이 이탈률에 훨씬 치명적이다. NNGroup(2022) 연구에 따르면 로그인/인증 오류 3회 이상 시 사용자 약 92%가 재시도 대신 이탈을 선택한다 [^7]. Baymard Institute(2024) 조사에서도 불필요한 보안 단계는 "too complicated process" 이탈 사유(18%)에 포함된다 [^8].

## 4. Google reCAPTCHA 공식 권장사항

### 4.1 버전별 권장 배치

| 버전 | 권장 방식 | 토큰 유효시간 |
|------|----------|-------------|
| reCAPTCHA v2 (Checkbox) | 폼 내부 위젯, submit 연동 | 약 2분 [^1] |
| reCAPTCHA v2 (Invisible) | 버튼 클릭 시 자동 검증 | 약 2분 [^1] |
| reCAPTCHA v3 (Score) | 페이지 로드 시 백그라운드 점수 산출 | 약 2분 [^2] |
| reCAPTCHA Enterprise | v3 동일, 추가 위험 분석 | 약 2분 [^2] |

Google은 **사용자 마찰(friction) 최소화**를 핵심 설계 원칙으로 명시한다. reCAPTCHA v3 공식 문서에 "returns a score for each request **without user friction**"이라고 명시되어 있다 [^2]. 별도 페이지 분리를 권장하지도, 금지하지도 않는다. 핵심은 "마찰을 줄여라"이다.

### 4.2 현재 서비스 상황과의 관계

현재 서비스의 CAPTCHA 유효시간이 30초라면, 이는 Google reCAPTCHA 기본값(약 2분) [^1]과 다르다. **자체 CAPTCHA이거나, 서버 측에서 유효시간을 별도로 제한**하고 있을 가능성이 있다. 만약 후자라면 서버 측 유효시간 연장도 검토 대상이다.

## 5. 법적 요건 (한국 기준)

### 5.1 필수 동의 항목

| 법적 요건 | 근거 법률 | 내용 |
|-----------|----------|------|
| 이용약관 동의 | 약관규제법 제3조 (약관의 명시·설명 의무) [^4], 전자상거래법 제13조 (신원·거래조건 정보 제공) [^5] | 서비스 이용약관 사전 고지 및 동의 |
| 개인정보 수집·이용 동의 | 개인정보보호법 제15조 [^3] | 수집 항목, 목적, 보유기간 명시 후 동의. 동의 거부 시 불이익 내용 고지 의무 |
| 14세 미만 확인 | 개인정보보호법 제22조 [^3] | 법정대리인 동의 필수. 각 동의 사항을 구분하여 명확히 표시(선택/필수 구분) |
| 본인인증 | 정보통신망법 제23조의3 [^6] | 휴대폰/아이핀 인증 (법적 강제가 아닌 사업자 자율, 주민등록번호 수집 제한에 따른 대체 수단) |

### 5.2 CAPTCHA 관련 법적 규정

CAPTCHA 배치 위치(분리/통합)에 대한 법적 규정은 **존재하지 않는다.** 개인정보보호법 제29조, 정보통신망법 제45조 등에서 기술적 보안 조치 의무를 규정하나, CAPTCHA 사용 여부나 배치 위치를 특정하는 조문은 없다 [^3][^6]. 봇 방지는 서비스 제공자의 보안 정책 영역이다.

### 5.3 동의 수집 순서

개인정보보호법상 **개인정보 수집 전에 동의**를 받아야 한다. 1안 구조에서는 페이지1(CAPTCHA)에는 개인정보가 없고, 페이지2(회원정보 입력)에 동의 UI를 배치하면 법적 순서가 맞다.

## 6. 업계 채택 현황

### 6.1 주요 서비스 사례

| 서비스 | 구조 | CAPTCHA 유형 | SMS 인증 |
|--------|------|-------------|---------|
| Naver | 약관 → 정보 입력 + CAPTCHA → 완료 | reCAPTCHA v2 + 자체 | SMS 인증 통합 |
| Kakao | 약관 → 정보 입력 → 완료 | Invisible | SMS 별도 팝업 |
| 쿠팡 | 약관 → 정보 입력 → 완료 | reCAPTCHA v3 | SMS 별도 처리 |
| Google | 정보 입력 + CAPTCHA → 완료 | reCAPTCHA (자사) | SMS 별도 스텝 |
| Facebook/Meta | 정보 입력 → 완료 | 조건부 CAPTCHA | SMS 별도 스텝 |

### 6.2 채택률 종합

일반적으로 2안(통합형)이 주류다. Formstack(2021) 보고서에 따르면 멀티스텝 폼이 단일 폼 대비 전환율 약 86% 향상을 보이지만 [^9], 이는 단계를 적절히 분할한 경우이며 단계 수 과다는 역효과를 낳는다 [^8]. 이들 서비스 대부분은 **reCAPTCHA v3(invisible) 또는 토큰 유효시간 2분 이상**을 사용하며, SMS 인증을 별도 API 호출로 분리하여 CAPTCHA 토큰과 SMS 인증의 생명주기를 이미 분리하고 있다.

**CAPTCHA 유효시간이 30초이고 SMS 인증까지 단일 토큰으로 묶는 구조는 업계에서 사례를 찾기 어렵다.**

## 7. CAPTCHA 만료 UX 문제 상세 분석

### 7.1 타임라인

```
0초    CAPTCHA 클릭 (토큰 발급)
 │
3초    휴대폰 번호 입력 완료
 │
5초    "인증번호 발송" 클릭 → SMS 발송 요청
 │
10초   SMS 수신 (최선의 경우)
 │
20초   인증번호 입력 완료 (최선의 경우)
 │
30초   ██ CAPTCHA 만료 ██
 │
40초   SMS 수신 (통신사 지연 시)
 │
60초+  SMS 수신 (트래픽 폭주 시)
```

최선의 시나리오(SMS 즉시 수신 + 빠른 입력)에서도 20초가 소요되어 겨우 통과한다. 통신사 지연이 조금이라도 있으면 30초를 초과한다.

### 7.2 사용자 경험 루프

```
CAPTCHA 인증 → SMS 발송 → (대기) → 인증번호 입력 → "CAPTCHA 만료" 오류
     ↓
CAPTCHA 재인증 → SMS 재발송 → (대기) → 인증번호 입력 → "CAPTCHA 만료" 오류
     ↓
    이탈
```

## 8. 개선안

### 8.1 개선안 A — 1안 채택 (CAPTCHA 페이지 분리 + 세션 저장)

현재 제시된 1안 그대로다. CAPTCHA를 별도 페이지에서 완결하고 세션에 저장한다.

```
페이지1: CAPTCHA
  └─ CAPTCHA 클릭 → 서버: 세션에 captcha_passed = true 저장 → 페이지2 이동

페이지2: 회원정보 입력
  ├─ 약관/개인정보 동의
  ├─ 회원정보 폼
  ├─ 휴대폰 번호 + [인증번호 발송] → 서버: 세션의 captcha_passed 확인 후 SMS 발송
  ├─ 인증번호 입력 → 서버: 세션 기반 인증번호 대조
  └─ [가입하기]

페이지3: 가입 완료
```

| 장점 | 단점 |
|------|------|
| CAPTCHA 만료 문제 완전 해소 | 페이지 1스텝 추가 |
| 구현 변경 최소 (세션 저장만 추가) | CAPTCHA 단독 페이지의 목적 불명확감 |
| 봇을 폼 도달 전에 선차단 | |

### 8.2 개선안 B — 2안 유지 + CAPTCHA 소비 시점 분리

2안(통합형) 구조를 유지하되, CAPTCHA 토큰을 SMS 발송 API 호출 시점에서 서버 사이드로 1회 소비하고, 이후는 세션으로 관리한다.

```
페이지1: 회원정보 입력
  ├─ 약관/개인정보 동의
  ├─ 회원정보 폼
  ├─ CAPTCHA + 휴대폰 번호 + [인증번호 발송]
  │     └─ 발송 클릭 시:
  │          서버 → CAPTCHA 토큰 검증 (1회 소비, 여기서 완료)
  │          서버 → 세션에 sms_captcha_passed = true 저장
  │          서버 → SMS 발송
  ├─ 인증번호 입력
  │     └─ 서버 → 세션의 sms_captcha_passed 확인 + 인증번호 대조 (CAPTCHA 무관)
  └─ [가입하기]

페이지2: 가입 완료
```

| 장점 | 단점 |
|------|------|
| CAPTCHA 만료 문제 해소 | 서버 로직 변경 필요 (CAPTCHA 소비 시점 분리) |
| 페이지 수 유지 (2페이지) | CAPTCHA 소비 후 세션 악용 방지 보완 필요 |
| 업계 표준 구조 유지 | |

### 8.3 개선안 C — reCAPTCHA v3 전환 (Invisible)

CAPTCHA를 사용자에게 보이지 않는 reCAPTCHA v3로 전환한다. 페이지 로드 시 백그라운드로 점수를 산출하고, SMS 발송 요청 시 서버에서 점수 기반으로 봇 여부를 판단한다. Stanford/Moz 연구에 따르면 CAPTCHA 도입 시 스팸 95% 감소하지만 정상 제출 약 3.2% 감소하는데 [^10], invisible 방식은 이 손실을 제거한다.

```
페이지1: 회원정보 입력
  ├─ (reCAPTCHA v3 백그라운드 동작 — 사용자에게 보이지 않음)
  ├─ 약관/개인정보 동의
  ├─ 회원정보 폼
  ├─ 휴대폰 번호 + [인증번호 발송]
  │     └─ 발송 클릭 시: reCAPTCHA v3 토큰 즉시 생성 → 서버 검증 → SMS 발송
  ├─ 인증번호 입력
  └─ [가입하기]

페이지2: 가입 완료
```

| 장점 | 단점 |
|------|------|
| CAPTCHA 만료 문제 원천 제거 | CAPTCHA 제공사 변경 또는 버전 업그레이드 필요 |
| 사용자 마찰 제로 | v3 점수 기반이라 봇 차단 정확도 조정 필요 |
| 토큰을 발송 버튼 클릭 시 즉시 생성하므로 만료 무관 | |

### 8.4 개선안 비교 종합

| 항목 | A (1안 채택) | B (2안 + 소비 분리) | C (reCAPTCHA v3) |
|------|-------------|-------------------|-----------------|
| **만료 문제 해소** | O | O | O |
| **구현 변경량** | 최소 (세션 저장 추가) | 중간 (서버 로직 변경) | 대 (CAPTCHA 교체) |
| **페이지 수** | 3 | 2 | 2 |
| **사용자 마찰** | 약간 증가 (1스텝 추가) | 현행 유지 | 감소 (invisible) |
| **봇 차단 효과** | 유지 | 유지 + 보완 필요 | 조정 필요 |
| **업계 표준 부합** | 소수 패턴 | 주류 패턴 | 최신 트렌드 |

## 9. SMS 무차별 발송 방지 — 보완 수단

어떤 개선안을 선택하든, CAPTCHA만으로는 SMS 무차별 발송을 완전히 차단할 수 없다. 다음을 병행한다.

| 수단 | 구현 | 효과 |
|------|------|------|
| **번호별 일일 제한** | 동일 번호 하루 5회 초과 차단 | 특정 번호 대상 폭격 방지 |
| **재발송 쿨다운** | 발송 후 60초간 재발송 불가 | 연속 클릭 방지 |
| **IP 기반 Rate Limit** | 동일 IP에서 10분 내 N회 초과 차단 | 단일 출처 대량 발송 방지 |
| **세션당 발송 제한** | 1 세션 3회 초과 시 CAPTCHA 재인증 요구 | 세션 악용 방지 |
| **인증번호 유효시간** | 발송 후 3~5분 이내 입력 필수 | 시간 제한은 인증번호에서 별도 관리 |

## 10. 결론

### 10.1 현행 문제 요약

| 항목 | 내용 |
|------|------|
| **문제** | CAPTCHA 유효시간(30초) < SMS 인증 완료까지 소요시간(15초~2분+) → 정상 사용자 인증 실패 |
| **원인** | 2안 구조에서 CAPTCHA 토큰이 SMS 인증 완료 시점까지 유효해야 하는데, 30초로는 불가능 |

### 10.2 개선안 권장 순위

| 순위 | 개선안 | 이유 |
|------|--------|------|
| **1위** | **A — 1안 채택** (CAPTCHA 분리 + 세션 저장) | 구현 변경 최소, 만료 문제 구조적 해소, 즉시 적용 가능 |
| **2위** | **B — 2안 유지 + 소비 시점 분리** | 페이지 수 유지, 서버 로직 변경 필요하지만 업계 표준 부합 |
| **3위** | **C — reCAPTCHA v3 전환** | 최선의 UX이지만 CAPTCHA 교체에 따른 변경량이 큼 |

### 10.3 최종 판단

1안이 일반적으로는 소수 패턴이지만, **현재 서비스의 조건(CAPTCHA 유효시간 30초 + SMS 인증 필수)에서는 1안이 가장 합리적이다.** CAPTCHA를 별도 페이지에서 완결하고 세션에 저장하는 것이 만료 문제를 구조적으로 제거하는 가장 단순한 방법이며, 구현 변경도 최소다.

업계에서 2안이 주류인 이유는 대부분의 서비스가 reCAPTCHA v3(invisible) 또는 토큰 유효시간 2분 이상을 사용하기 때문이다. **CAPTCHA 유효시간 30초라는 제약 조건 하에서는 업계 일반 채택률보다 서비스 실제 환경에 맞는 구조를 선택하는 것이 올바르다.**
