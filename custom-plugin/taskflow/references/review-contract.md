# 분리 루프 공유 계약 (review-contract)

개발 Agent ↔ cold 리뷰어 분리 루프의 공유 규칙 SSOT. `code`·`code-loop`·`review`·`tick`·`watch`·에이전트 정의가 이 파일을 참조한다 — 커맨드끼리 서로의 본문을 참조하지 않기 위해 커맨드 밖으로 뺐다 (2026-09-28, 원문 무수정 이동: `watch.md` §"코드 축" · `tick.md` §"step 개발"·§"하니스 자동 상속"·§"카탈로그 미등재 fallback").

## 코드 축 — 변경분 리뷰 (무인 코드리뷰 계약 SSOT)

**본 절이 무인 코드리뷰 계약의 SSOT 다 — `/taskflow:tick` 의 리뷰 루프도 같은 계약을 쓴다** (`tick.md` §"step 코드리뷰 루프" 는 여기 포인터). 계약이 두 곳에 복붙되면 갈라지고, 갈라지는 순간 tick 이 통과시킨 것을 watch 가 **다른 기준으로** 반려해 왕복이 되살아난다.

**`reviewer-correctness` · `reviewer-design` Agent 2개를 병렬 spawn** 해 **변경분만** 리뷰한다 (`subagent_type: taskflow:reviewer-correctness` · `taskflow:reviewer-design` — 플러그인 agent 는 `plugin:name` 형식이다. 정의 = `custom-plugin/taskflow/agents/reviewer-correctness.md` · `reviewer-design.md`). 전체 코드베이스 감사가 아니다.

- **본체가 조립하는 것은 입력뿐이다** — worktree diff(또는 커밋 범위) + 그 step 문서의 §계획·DoD + **개발 Agent 반환의 `BASELINE`**. 두 리뷰어는 **같은 입력**을 받는다.
- **`BASELINE` 을 빼지 않는다.** 리뷰어는 `근거: 실행` 을 계약으로 요구받는데(§6) 어느 명령이 이 변경을 덮는지를 매번 새로 찾는다 — 그 탐색이 전량 스위트로 넓히려는 유인이 되고, 이 환경에서 그건 실 테이블을 갈아엎는다. 개발 Agent 가 이미 돌려서 알고 있는 것을 전달만 하면 된다. 없으면(구 경로·문서 축) 그 사실을 입력에 명시한다 — 조용히 비우면 리뷰어가 스스로 찾는다.
- 리뷰 관점 7축은 **둘로 갈라져 있다** — 기능 정합(§1 경계값·예외·회귀·동시성 / §5 호출부 전수 / §6 실행 검증) = `reviewer-correctness`, 설계 정합(§2 보안 / §3 단순성 / §4 재사용 / §7 범위) = `reviewer-design`. 판정 등급·"코드 수정 금지"·반환 양식과 함께 **전부 agent 정의에 박혀 있다**. 여기서 다시 적지 않는다.
- **한 패스로 7축을 보지 않는다 (2026-08-19 축 분리).** 실측이 필요한 무거운 축(§6 돌려봐야 검증)이 얕아진다 — 구 `cold-reviewer` 정의 스스로가 그렇게 적어뒀다.
- 반환 = 리뷰어별 `VERDICT: CLEAN | FINDINGS` + Critical~Low 지적의 `file:line` (양식 SSOT = agent 정의).

**두 반환을 합치는 규칙 (본 절이 SSOT — 2인을 띄우는 모든 경로가 이걸 쓴다).**

| 상황 | 처리 |
|------|------|
| 같은 `file:line` 에 양쪽 지적 | **높은 등급을 채택**한다 |
| 상대 축 태그(`[design]`·`[correctness]`)가 붙은 지적 | **본체가 등급을 매기지 않는다.** 루프 경로면 다음 라운드에 해당 리뷰어가 판정하고, 1회 경로면 태그를 단 채로 잔여에 남긴다 |
| 한쪽 `CLEAN` · 한쪽 `FINDINGS` | 합본은 `FINDINGS` 다. 한 축이 깨끗한 것은 종료 근거가 아니다 |

**왜 프롬프트가 아니라 agent 정의인가.** 계약을 매번 프롬프트로 조립하면 라운드마다 문구가 달라지고 그 편차가 곧 리뷰 편차다(아래 §"watch 의 리뷰는 재확인이다" 가 인정하는 그 편차). 정의에 박아두면 spawn 마다 변하는 것이 diff 하나뿐이 된다.

**리뷰어는 코드를 고치지 않는다.** 두 정의 모두 Edit·Write 도구가 없는 것이 그 강제다 (`dev-team` FE 멤버를 `Explore` 로 두는 것과 같은 기계적 차단 — 지시문은 어길 수 있어도 없는 도구는 못 쓴다). `simplify` 처럼 수정까지 하는 경로를 타지 않는다 — 무인 루프가 리뷰하면서 코드를 바꾸면 리뷰 대상 자체가 움직인다.


## step 개발 (Agent 위임 — 본체는 코드를 쓰지 않는다, 필수)

step 개발은 **`step-developer` Agent 1개**에 위임하고(`subagent_type: taskflow:step-developer` — 플러그인 agent 는 `plugin:name` 형식이다. 정의 = `custom-plugin/taskflow/agents/step-developer.md`), tick 본체는 **지휘·기록·상태 전이만** 한다. 개발자와 "리뷰 지적 수정자" 가 같은 인격이면 자기가 고친 것을 자기가 통과시키는 확인 편향이 남는다 — 리뷰를 cold 로 뺀 것과 같은 이유다.

**코드를 쓰는 기준(단순성·재사용·"돌려봐야 검증"·호출부 전수·범위 고수)·금지사항·반환 양식은 agent 정의에 있다.** 리뷰어와 같은 이유로 프롬프트에 매번 적지 않는다. 본체가 조립하는 것은 **worktree 경로 + 그 step 의 §계획·§파급면·§결함면·DoD + (반려 소비 시) 호출부 grep 결과** 뿐이다.

| 주체 | 하는 일 |
|------|--------|
| tick 본체 | claim · worktree 생성 · 개발 Agent 지휘 · 리뷰어 spawn · 문서 기록 · 상태 전이 |
| **개발 Agent** (warm, 1개) | 코드 작성 + 리뷰 지적 수정 |
| 리뷰 Agent (cold, 라운드마다 신규) | 판정만 · 코드 수정 금지 (§"step 코드리뷰 루프") |
| **적대적 red-team** (cold, 게이트 1~2회) | 클린 반증만 · 코드 수정 금지 (§"적대적 검증 게이트") |

**개발 Agent 는 라운드마다 새로 뜨지 않는다.** 최초 1회 spawn 하고 리뷰 지적은 `SendMessage` 로 **같은 Agent** 에 이어 보낸다. 새로 띄우면 §계획·DoD·이미 쓴 코드를 매 라운드 다시 읽어야 하고, 리뷰 한도가 5회라 최악에 5회 재구축이다. 갈아끼우는 쪽은 리뷰어뿐이다.

**`isolation: worktree` 를 쓰지 않는다 (필수).** 본체가 만든 worktree 경로를 프롬프트로 넘겨 **그 안에서** 작업시킨다. isolation 을 켜면 하니스가 별도 worktree 를 파서 커밋이 그 step 의 `wip/*` 가 아닌 곳에 쌓이고, `머지 전 리뷰 포인트` 에 적은 경로와 실제 커밋 위치가 갈라진다 — watch 의 머지 사다리가 그 경로를 믿고 정착시키므로 어긋남이 조용히 진행된다. tick 은 단일 워커라 격리가 애초에 불필요하다 — 병렬이 필요하면 `tick-loop N` 이 **슬롯마다 독립 프로세스**를 띄우므로 프로세스 경계가 격리를 대신한다.

**Agent 는 코드만 쓴다.** §실행·`## 변경 영향 기록`·Before/After 는 **본체가** Agent 반환(`FILES`/`TESTS`/`NOTES`)으로 쓴다 (§"step 상세 기록" 재사용 — Agent 에 문서 양식을 가르치지 않는다).

**커밋도 본체가 한다.** 리뷰어가 보는 입력이 **미커밋 diff** 라 개발 Agent 가 중간에 커밋하면 리뷰어에게 빈 diff 가 간다. 커밋은 리뷰 루프가 클린이 된 뒤 4단계에서 본체가 한다 (`머지 전 리뷰 포인트` 기록과 같은 시점).

**두 Agent 모두 모델이 정의에 고정돼 있다 — 리뷰어·개발자 모두 `sonnet`.** `tick-loop.sh:29` 의 세션 기본값이 `sonnet` 이라(`${TICK_LOOP_MODEL:-sonnet}`) **모델을 생략하면 무인 경로에서만 sonnet 을 상속**한다 — `orchestration` §1.1 이 전제하는 "생략 = opus 상속" 이 여기서만 깨진다. 값이 지금 세션 기본값과 우연히 같아도 **명시는 유지한다** (기본값이 바뀌면 조용히 따라 움직인다). 본체(claim·문서 기록·상태 전이)는 기계적이라 sonnet 으로 충분하다. **리뷰어가 최종 방어선이라는 사실은 하향 후에도 변하지 않는다** — 개발자는 §계획·DoD 라는 대조 기준을 받고 들어가지만 리뷰어는 그것을 만들어내야 하고, 놓친 결함은 리뷰어 쪽에서만 새어 나간다. 관측 = 반려 라운드 수 + **머지 후 결함** (Changelog 2026-08-10).

**라운드 종료마다 변경 실재를 확인한다.** Agent 가 코드를 쓰지 않고 텍스트만 돌려주는 실패 모드가 실재한다.

```bash
git -C "$WORKTREE" status --porcelain      # 빈 결과 = 개발 실패 (리뷰로 넘기지 않는다)
```

빈 결과를 그대로 리뷰에 넘기면 리뷰어가 빈 diff 를 `[High]` 판정 불가로 되돌려 라운드만 소진된다.

**hook 은 자동 상속된다** (아래 §"하니스 자동 상속"). 개발 Agent 의 Write·Bash 에도 worktree-enforce·dangerous-ops-guard·§3 가드가 걸리므로 룰 재주입이 불요하다. 미등재 세션 대응은 §"카탈로그 미등재 fallback".

## 하니스 자동 상속 (2026-07-23 실측)

**subagent 도구 호출에도 PreToolUse hook 이 적용된다** — subagent 의 Write 를 `worktree-enforce` 가, `rm -rf` 를 `dangerous-ops-guard` 가 차단함을 실측 확인(2026-07-23, Agent probe). 따라서 tick 이 spawn 하는 개발·리뷰 Agent 에도 하니스 룰(gate·worktree·§3 가드)이 **자동 상속**되고, Skill 도구로 `/taskflow:tick` 을 호출하는 쪽(`tick-loop` 의 자식 세션)도 tick 명세의 claim/auto/step 로직을 그대로 물려받는다 → **호출자별 룰 재구현 0.**

이것이 무인 경로가 "§3 우회 통로" 가 아닌 기계적 근거다 — 지시문이 아니라 hook 이 막는다.

## 카탈로그 미등재 fallback (SSOT — slash·agent 공통)

**카탈로그는 세션 시작 시 로드된다.** 그래서 정의를 만든 **당일 세션**에서는 신규 slash·신규 agent 가 미등재고, 다음 세션부터 정상 호출된다. 무인 루프는 그 하루를 멈출 수 없으므로 fallback 을 탄다.

| 대상 | 미등재 시 |
|------|----------|
| **slash** (`taskflow:tick` 등 Skill 호출) | 그 커맨드 문서의 해당 단계를 `bash` 로 직접 수행 (예: tick 1단계 = `working_scan` + `registry_claim`) |
| **agent** (`taskflow:reviewer-correctness` · `taskflow:reviewer-design` · `taskflow:step-developer` · `taskflow:adversary`) | `general-purpose` 로 spawn 하되 **정의 파일 전문을 프롬프트 앞에 붙이고 `model` 을 호출 파라미터로 명시** — 리뷰어 = `sonnet`, 개발자 = `sonnet`, `taskflow:adversary` = `opus`. **리뷰어 2개는 fallback 에서도 각각 띄운다** (한 프롬프트에 두 정의를 합치면 축 분리 이유였던 §6 얕아짐이 그대로 돌아온다) |

**agent fallback 에서 `model` 을 생략하면 안 된다.** 정의를 안 타면 모델도 세션 기본값을 상속한다(`tick-loop.sh` = sonnet). 지금은 두 값이 우연히 목표값과 같지만 **세션 기본값이 바뀌면 양쪽 다 조용히 흔들린다.** 상속에 기대지 말고 두 값을 각각 적는다. 계약 없이 도는 것보다 정의 전문을 붙여 도는 편이 낫다.

# 루프 계약 (2026-09-28 `code.md` 에서 원문 무수정 이동)

## 대조 기준 — 1단계를 건너뛰지 않는다

문서 기반 경로는 §계획·DoD 가 리뷰 기준이 된다. 여기엔 그게 없으므로 **1단계에서 확정한 성공 기준이 그 자리를 대신한다.** 이걸 안 적고 개발에 들어가면 리뷰어가 대조할 것이 없어 `VERDICT: FINDINGS` + `[High] 판정 불가` 로 되돌아온다 (fail-closed — 두 정의에 그렇게 박혀 있다).

성공 기준은 검증 가능해야 한다. "동작하게" 는 기준이 아니다 — "이 함수가 X 입력에 Y 를 반환" 또는 "기존 테스트 N개 green 유지" 처럼 쓴다.

### 파급면·결함면을 적는다 — 형식이 바뀔 때만

**저장 형식·시그니처·응답 스키마를 바꾸는 요청이면 여기에 파급면·결함면도 적는다** — 그 값을 읽는 쪽(read 경로·형제 호출부)과 틀릴 수 있는 축(경계값·예외·타입·회귀·동시성). 문서 경로는 `plan.md` §"파급면·결함면 — 골격 무관 공통" 이 이걸 step 에 박아주지만, 여기엔 그 단계가 없어서 1단계가 안 적으면 아무도 안 적는다. 리뷰어는 그 축을 그대로 보므로 안 적힌 만큼 반려로 돌아온다.

### 테스트 범위를 케이스 단위로 적는다

예: `경계값 테스트: null · 빈 배열 · 음수 잔액 3케이스`

이게 없으면 리뷰어가 커버리지 축을 라운드마다 새로 파고 **`Medium` 이 수렴하지 않는다.** `Medium` 을 종료 조건에 넣을 수 있는 것은 이 한 줄 덕이다.

### 비목표를 같이 적는다

**성공 기준만큼 중요하다.** 콜드 리뷰어는 컨텍스트가 없어서 **안 적힌 것을 상상해서 채운다** — 상위 필터가 이미 처리하는 인증을 "누락" 으로, 다루지 않기로 한 재시도를 "멱등성 미비" 로 낸다.

그 지적이 개발자에게 가면 방어 코드가 늘고, 그 코드는 다음 라운드에 과설계로 다시 잡힌다.

예시: `비목표: 인증·권한(상위 필터 소관) · 재시도·멱등성(이번 범위 아님) · 성능 최적화`

리뷰어는 여기 적힌 축을 `Low` + `[범위밖]` 로 흘리고 루프를 붙잡지 않는다.

### 크기 게이트 — 4개면 되돌린다

**검증 가능한 성공 기준이 4개 이상이면 이 커맨드로 받지 않는다.** 정지하고 `/taskflow:plan` 을 안내한다.

호출부 전수가 걸린 요청(시그니처·저장 형식 변경)은 라운드가 눈에 띄게 많이 나온다. 단발 루프에 넣으면 **캡을 소진한 뒤에야 크기 문제였다는 걸 알게 되고, 그때는 이미 5라운드를 태운 뒤다.** 앞에서 5초 판정하는 것이 싸다.

### 커밋 type·scope 도 여기서 확정한다

성공 기준 · 테스트 범위 · 비목표와 함께 커밋 **type·scope** 를 확정한다.

- **type** — push 스킬 §"type 목록" 10종 중 하나
- **scope** — push 스킬 §"scope 규칙": BE 는 모듈명 PascalCase, FE 는 페이지/기능 단위, 공통·인프라는 소문자, 여러 모듈에 걸치면 생략

나중에 정하면 **파생 변경(테스트·린터)에 휘둘려 매번 다르게 붙는다.** 그리고 **scope 가 생략될 만큼 여러 모듈에 걸친 요청이면 크기 게이트를 다시 본다** — 단발 루프가 감당할 범위가 아닐 가능성이 높다.

**문서 변경이 섞였을 때 type 을 어떻게 정하는가**

- 코드 파일 안의 **주석·docblock 은 `docs` 가 아니다.** 로직 변경의 일부이므로 요청 성격(`fix`·`feat`·`refactor`)을 그대로 쓴다.
- 별도 문서 파일(README·API 문서 등) 갱신이 코드 변경에 딸려 왔으면 **요청 성격을 따른다** — 기능 추가에 딸린 문서 갱신은 `feat` 이지 `docs` 가 아니다. 파생 변경은 type 판정에 넣지 않는다는 원칙 그대로다.
- **문서만** 고치는 요청이면 `docs` 다.
- working/ 문서·`## 변경 영향 기록` 은 애초에 커밋 대상이 아니다 — `step-developer` 는 문서를 쓰지 않고(§"하지 않는 것"), 이 커맨드는 문서를 만들지 않는다(§"무엇을 하지 않는가").

**요청 자체가 "코드도 고치고 문서도 갱신" 이면 의도가 둘이다.** 1단계에서 성공 기준이 두 축으로 갈리므로 크기 게이트에 먼저 걸린다. `/taskflow:code` 로 받지 말고 `/taskflow:plan` 으로 넘기거나 두 번 나눠 부른다. push 스킬 §"핵심 규칙" 3(1커밋 = 1변경)을 커밋 시점이 아니라 **1단계에서** 지키는 것이다.

## 루프 종료 조건

**`Critical` · `High` · `Medium` 이 모두 0이면 종료 후보다.** 확정은 적대적 검증 게이트를 통과한 뒤다.

| 상태 | 처리 |
|------|------|
| C·H·M 0 | §"적대적 검증 게이트" 로 |
| `Low` 만 잔존 | **종료를 막지 않는다.** ①②③ 은 4-ter 린터, ④ `[범위밖]` 은 residual |
| C·H·M 중 하나라도 ≥1 | 지적 합본을 개발 Agent 에 `SendMessage` → 재리뷰 (라운드 +1) |

캡은 **5회**다.

**`Medium` 을 종료 조건에 넣는 근거:** 목표가 결과 품질이므로 "머지 후 처리 가능" 을 종료 사유로 쓰지 않는다. `Medium` 이 수렴하지 않던 축은 사실상 테스트 커버리지 하나이고, 그건 1단계 테스트 범위 명시로 막는다 — 리뷰어는 명시된 케이스가 있으면 그 축을 더 파지 않는다.

**`Low` ①②③(내부 네이밍·미사용 import·주석 오탈자)을 라운드로 고치지 않는 이유는 비용보다 판정 때문이다** — 결함 수정과 미용 수정이 같은 diff 에 섞이면 다음 라운드가 무엇을 봐야 하는지 흐려진다 (`step-developer.md` §"리뷰 지적을 받았을 때"). 게다가 `Low` 는 등급 정의상 "지금도 앞으로도 의도대로 돈다" 이므로 안 고친 손실이 0이고, 종료 조건이 C·H·M 이라 `Low` 를 고쳐도 종료에 아무 영향이 없다. 다만 ①②③ 은 애초에 린터 소관이다. **리뷰어가 이걸 반복 지적하고 있다면 그건 결함이 아니라 린터 설정이 빠졌다는 신호다** — 루프를 늘리지 말고 4-ter 에서 기계로 처리한다. ④ `[범위밖]` 은 여기 해당하지 않는다. 비목표가 없었으면 `High`·`Medium` 으로 나왔을 건이라 린터가 손댈 수 없고, residual 로 남긴다.

## 적대적 검증 게이트 (2026-08-31~)

C·H·M 이 0이 되면 **종료 전에 `taskflow:adversary` 를 스폰한다.** 목표는 재검토가 아니라 **반증**이다 — 이 클린이 틀렸음을 재현으로 보이는 것.

`subagent_type: taskflow:adversary` · 계약 = `custom-plugin/taskflow/agents/adversary.md` (반환 양식 · 공격면 5축 · 재현 강제 · Edit/Write 부재). 여기 소관은 **스폰 시점 · 재진입 · 캡** 셋뿐이다.

**입력에 라운드 로그 전문을 반드시 넣는다.** 무엇을 방어했는지 모르는 red-team 은 리뷰어와 같아지고, 그러면 게이트를 붙인 값이 0이다 (계약에 fail-closed 로 박혀 있다 — 클린 근거가 없으면 `BROKEN: 판정 불가` 로 되돌아온다).

| 입력 | 출처 |
|------|------|
| 변경분 diff (untracked 포함) | worktree |
| 대조 기준 — 성공 기준 · 테스트 범위 · 비목표 | 1단계 확정분 |
| **클린 판정 근거 — 라운드 로그 전문** | §"라운드 이력을 넘긴다" 형식 그대로, `REBUTTED-ACCEPTED` 포함 |
| `BASELINE` (전·후) | 개발 Agent 최종 반환. **공격면 4번(수정이 만든 결함)의 출발점**이고, 없으면 여기서도 덮는 명령을 새로 찾다가 전량 스위트로 넓힌다 |

| 결과 | 처리 |
|------|------|
| `UPHELD` | 종료. `시도` 나열을 보고에 그대로 옮긴다 |
| `BROKEN` | 재현 명령·출력을 개발 Agent 에 `SendMessage` → 수정 → **정규 루프 재진입**(리뷰어 2인 1라운드). 그 리뷰가 `CLEAN` 이면 → 다시 이 게이트로. **`FINDINGS` 면 → 게이트를 닫고 잔여로 넘긴다 — 정규 루프로 되돌리지 않는다**(`code-loop.md` §adv-loop 과 동일 분기, 되돌리면 캡 무제한 통로가 생긴다) |
| `BROKEN: 판정 불가` | 입력 조립이 틀린 것이다. 코드 문제가 아니므로 재진입이 아니라 **입력을 채워 재스폰**한다 (캡에 넣지 않는다) — `code-loop.md` 의 `BROKEN-UNDECIDED` 와 같은 처리 |

**캡은 2회다.** 두 번째도 `BROKEN` 이면 클린으로 만들지 않는다 — 재현물을 잔여에 남기고 보고한다.

**게이트발 재진입 라운드(리뷰어 2인 1라운드)는 정규 캡(5회)에 계상한다.** 정규 캡이 남아 있지 않으면 재진입하지 않고 재현물을 잔여로 넘긴다 — 게이트 캡 2회는 **정규 캡을 늘리는 통로가 아니다.** 구 4-bis 가 "캡에 포함, 최대 1회만 재진입" 으로 막아두던 자리이고, 여기가 비면 클린 직전에 라운드가 무한히 열린다.

**정규 루프 캡(5회)을 소진하고 끝난 경우에는 돌리지 않는다.** 이미 blocker 가 남아 있어 깰 것이 없다.

**`UPHELD` 는 통과 도장이 아니다.** 시도 나열이 비어 있으면 그 반환은 계약 위반이므로 재스폰한다 (캡에 넣지 않는다).

### 왜 무이력 리뷰어 재스폰을 대체했는가

이전 4-bis 는 `reviewer-correctness` 를 이력 없이 한 번 더 띄우는 것이었다. 근거는 "이력을 받은 리뷰어는 '이미 처리됨' 프레임이 생겨 놓친다" 였고, 그 관찰 자체는 맞다.

**틀린 것은 처방이다.** 같은 정의·같은 판정축·같은 절제("명시된 케이스는 더 파지 않는다")를 다시 띄우면 **프레임만 지우고 사각지대는 그대로 둔다.** 리뷰어가 못 본 이유는 이력을 봐서가 아니라 **대조 기준에 맞춰 보라고 계약돼 있어서**다. 그 기준의 틈은 기준을 지키는 역할이 볼 수 없다.

그래서 눈을 새로 뜨는 대신 **목표를 뒤집었다** — 판정이 아니라 반증, 나열이 아니라 재현 1건, 기준 준수가 아니라 기준 공격. 백지 판정이 필요했던 것이 아니라 **적대적 판정이 필요했다.**

## 기준선을 교차 확인한다

개발 Agent 는 착수 전과 반환 전에 **같은 명령**을 돌려 `BASELINE` 전·후를 붙여온다 (`step-developer.md` §"돌려봐야 검증"). 본체가 볼 것은 **그 두 명령이 같은가** 하나다 — 다르면 대조가 아니라 새 관측이고, "고쳤다" 의 근거가 없다.

| 반환 | 처리 |
|------|------|
| 전·후 명령 동일 · 전 red → 후 green | 정상. 리뷰어 입력에 그대로 동봉한다 |
| 전·후 명령 불일치 · `BASELINE` 부재 | 같은 명령으로 재실행을 지시한다. **라운드로 세지 않는다** — 개발 실패가 아니라 관측 실패다 |
| 착수 전 **재현 실패** (`NOTES`) | **고치게 하지 않는다.** 요청 자체가 틀렸거나 이미 해소된 것일 수 있으므로 정지 + 보고 |
| 후의 테스트·assertion 수가 전보다 감소 | 회귀다. `exit 0` 이어도 그렇다 (phpunit 은 fatal 에도 `0`) |

**리뷰어 입력에 `BASELINE` 을 동봉한다.** 리뷰어는 `근거: 실행` 을 계약으로 요구받는데 **어느 명령이 이 변경을 덮는지**를 매번 새로 찾고 있다 — 라운드 로그의 `근거실행` 비율이 낮게 나오던 자리이고, 전량 스위트로 넓혀서 뚫으려는 유인도 여기서 생긴다.

**재현 실패를 반려로 다루지 않는다.** 이 자리에서 정지하는 것이 이 절의 값 전부다 — 재현 없이 고치면 원인 귀속이 안 되고, 실측으로 확정처럼 적힌 원인 2개 중 검증된 것은 1개였다. 판별력 0인 수정이 클린을 달고 남는다.

**`code-loop.sh` 자동 러너는 명령 문자열 대조를 넘어 실제로 재실행한다 (2026-09-22~).** `BASELINE` 이 `green N tests, M assertions` 형식이면 셸이 같은 명령을 직접 돌려 그 수를 대조한다(`custom-plugin/taskflow/bin/code-loop.sh` `verify_baseline_counts`) — 그 외 형식(diff·git status 류)은 여전히 문자열 대조까지만 하고 판정은 리뷰어에게 남긴다. 불일치는 리뷰 라운드 전에 재보고를 2회까지 요청하되, 그래도 안 풀리면 런을 막지 않고 리뷰어에게 넘긴다 — 이 재실행은 리뷰어 토큰을 아끼는 전처리이지 리뷰어를 대신하는 판정자가 아니다.

**리뷰어 판정에도 같은 재실행을 대칭 적용한다 (2026-09-22~).** 리뷰어가 인용하는 `` `명령` → OK (N tests, M assertions) `` idiom 도 셸이 직접 재실행해 대조한다(`verify_rev_gate`). dev측(`BASELINE:`/`FILES:`)과 달리 리뷰어 반환 양식엔 구조화 필드가 없어 — 실측(rev 문서 406건에서 "무변경"·"바이트 일치" 서술 확인, 그 중 하나는 "untracked 0건" 처럼 명령의 실제 측정 범위와 주장 범위가 어긋나는 사례였다) — "무변경"·"바이트 일치" 주장은 자동 대조 대상에서 뺐다. 리뷰어 계약에 신규 필드를 추가하지 않았다 — 자유서술과 중복 기재되거나 뉘앙스가 손실되는 쪽보다, idiom이 이미 일관된 이 1종만 다루는 쪽을 선택했다.

## 반박 판정은 본체가 한다

개발 Agent 가 `REBUTTED` 를 반환하면 **자동 수용도 자동 기각도 하지 않는다.** 근거를 직접 확인한다.

| 근거 | 확인 방법 |
|------|------|
| 도달 불가 | 붙여온 `git grep` 결과를 검토 — 호출부 전건이 뽑혔는가, 그 입력이 생성되는 경로가 정말 없는가 |
| 상위 처리 | 댄 `file:line` 을 Read — 그 코드가 실제로 그 축을 처리하는가 |
| 비목표 매칭 | 1단계에서 확정한 비목표와 대조 |

**수용** → 지적이 닫힌다. 다음 라운드 리뷰어에게 `REBUTTED-ACCEPTED` 로 넘겨 재개봉을 막는다.
**기각** → 근거 불충분을 알리고 수정을 지시한다. 라운드는 소비된 것으로 센다.

판정을 건너뛰고 통과시키면 **지적 회피 통로**가 되고, 전부 기각하면 반박 경로가 없는 것과 같다. 근거 3종 확인이 이 절의 값 전부다.

## 두 리뷰어를 합친다

라운드마다 `reviewer-correctness` · `reviewer-design` 을 **병렬 스폰**하고 지적을 합쳐 개발 Agent 에 넘긴다. 두 리뷰어는 **같은 이전 라운드 이력**을 받는다.

**합본 규칙(등급 겹침·상대 축 태그·한쪽 CLEAN)은 `review-contract.md` §"코드 축" 이 SSOT 다** — 2인을 띄우는 경로가 여기만이 아니라서 규약 쪽에 둔다. 여기 소관은 **루프 특유의 것 하나뿐이다: 상대 축 태그가 붙은 지적은 다음 라운드에 해당 리뷰어가 등급을 판정한다** (1회 경로엔 다음 라운드가 없어 태그째 잔여로 남는다).

## 정착은 1커밋으로

worktree 정착은 **squash 1커밋**이다. 라운드별 중간 상태를 master 이력에 남기지 않는다 (절차 = `custom-plugin/git/commands/merge.md` §"squash 정착").

**커밋 포맷은 `custom-plugin/git/skills/push/SKILL.md` §"커밋 메시지 컨벤션" 을 따른다** (type·scope·72자·명령형). 여기서 재정의하지 않는다.

1. **중간 커밋은 리뷰를 통과한 적이 없다.** 리뷰가 클린을 보증한 단위는 worktree 최종 상태 하나뿐이고, 커밋 단위를 그것과 일치시킨다.
2. **4-ter 린터 `--fix` 가 별도 커밋으로 남으면 `git blame` 이 오염된다** — 로직 변경 라인이 style 커밋으로 잡힌다.
3. 라운드별 커밋은 **리뷰 루프의 내부 사정이지 코드의 역사가 아니다.**

**"1커밋 = 1변경" 과 충돌하지 않는다** (push 스킬 §"핵심 규칙" 3). 여기서 "1변경" 은 파일 하나가 아니라 **하나의 의도 단위**다 — push 스킬 자신의 예시 `refactor(Auth): Phase 4C 완료 — DI 전환 150건+` 가 그 해석을 보인다. `/taskflow:code` 1회는 1단계 성공 기준 하나를 달성하는 단위이므로 그대로 1변경이다. 금지된 것은 **의도가 다른 것을 섞는 것**(feat + refactor)이고, 리뷰 루프가 파생시킨 테스트·린터는 같은 의도의 부속이다. 실제로 다른 의도가 섞였으면 1단계 크기 게이트가 걸렀어야 하는 요청이다.

**type 은 1단계 요청의 성격으로 정한다.** 리뷰 루프가 파생시킨 변경(경계값 테스트 추가 · 린터 정리 · 호출부 반영)은 type 판정에 넣지 않는다. 경계값 테스트가 5개 늘어도 요청이 `fix` 면 `fix` 다. 린터 정리는 push 스킬 정의상 "로직 무변경" 이므로 별개 변경이 아니다.

**커밋 메시지는 제목 한 줄이다.** 성공 기준·비목표·리뷰 라운드 수·파생 변경 목록·worktree 이름을 본문에 적지 않는다 — 성공 기준과 비목표는 **입력이지 결과가 아니고**, 라운드 수는 프로세스 메타데이터이며, 테스트·린터 변경은 `git show` 로 보이고, 잔여는 residual 문서 소관이다. 전부 응답 보고에만 남긴다.

본문을 쓰는 경우는 push 스킬 §"예시" 의 BREAKING CHANGE(`type(scope)!:` + footer) 뿐이다.

```
fix(Payment): 코인 차감 실패 시 잔액 원복 누락 수정
```
