이슈 여러 건을 **한 개발 Agent · 한 worktree** 에서 이어 고치고, 리뷰와 적대적 검증은 **이슈별 커밋 단위로 따로** 돌린다. 루프는 만들지 않는다 — 검증은 `/taskflow:code` 계약을 그대로 쓰고, 이 커맨드는 **무엇을 어떤 순서로 묶을지**만 정한다.

## 무엇을 하지 않는가

**Agent 를 이슈 수만큼 띄우지 않는다.** 개발은 **1개**다. 한 Agent 가 순서대로 편집하므로 파일 충돌이 원천적으로 없고, 전체 그림을 보고 있어 상수 이름·시그니처가 서로 어긋나지 않는다.

**worktree 를 이슈마다 파지 않는다.** range 당 1개다. 이슈마다 파면 체크아웃(수천 파일)과 `composer install`(수백 MB·수 분)이 이슈 수만큼 곱해진다.

**리뷰·게이트·캡을 재정의하지 않는다.** 커밋 하나를 보는 방식은 `/taskflow:code` 와 동일하다(리뷰 2인 루프 5회 → 적대적 검증 2회).

**그룹핑을 기계가 결정하지 않는다.** 파일 축까지는 명령으로 뽑지만 **같은 메서드인가**는 소스를 읽어야 알고, 그건 본체 판단이다(§3단계).

## 전제 — 경계는 worktree 가 아니라 커밋이 만든다

개발이 1개면 "동시에 고치다 서로를 덮는" 문제가 사라진다. 대신 **리뷰의 경계**를 따로 만들어야 하고, 그 수단이 커밋이다.

```
worktree 1개
 ├ commit A  (이슈 1)  → 리뷰 2인 + 게이트  ← git show A
 ├ commit B  (이슈 2)  → 리뷰 2인 + 게이트  ← git show B
 └ commit C  (이슈 3)  → 리뷰 2인 + 게이트  ← git show C
```

리뷰어에게 `git show <커밋>` 을 주면 그 이슈만의 diff 가 나온다. **전체 worktree diff 를 주면 안 된다** — 리뷰어는 "이 변경" 을 판정하는데 경계가 없으면 대조 기준과 어긋나 `판정 불가` 로 되돌린다.

## 흐름

```
1. 목록      : range → 이슈 집합. 남의 세션이 코드로 점유한 것 제외
2. 파일 축   : 관련 파일 → 연결요소. 커밋을 나눌 수 있는지 · 순서가 있는지 판정용
3. 합침 판정 : 같은 메서드를 고치는 쌍은 한 커밋으로 (본체가 소스로 확인 — 필수)
4. 배치      : 커밋 순서 + 진입 단계 표를 사용자에게 1회 제시 → 승인
5. 실행      : 개발 Agent 1개에게 전부 지시. 이슈마다 커밋을 끊게 한다
6. 검증      : 커밋별로 리뷰 2인 → 적대적 검증. 캡은 커밋마다 독립
7. 정착      : 이슈별 1커밋으로 정리해 develop ff
```

## 1단계 — 목록과 제외

```bash
# 도메인 축
awk -F'\t' '$2=="Member"{print $1}' docs/wbs/tools/iss-domain-map.tsv
# 번호 범위 축은 파일명 glob
```

**남의 세션이 코드로 잡은 것만 뺀다.** `git worktree list` 에 그 슬러그가 있거나, 최근 커밋(`git log --since` 3일)이 **코드 파일을 건드리면서** 그 번호를 언급하면 제외한다.

**문서 커밋은 점유가 아니다.** 등재·조치 절 갱신·상태 전이는 "누가 이 번호를 적었다" 는 뜻이지 코드를 잡고 있다는 뜻이 아니다. 이걸 점유로 세면 **등재된 거의 전부가 빠진다**(2026-09-15 실측 — Member 잔여 14건 중 5건이 등재 커밋만으로 걸렸다). `git log --name-only` 로 그 커밋이 만진 파일에 코드(php/js/ts/py/sql)가 있을 때만 제외한다.

**형제째 뺀다.** 제외된 이슈와 같은 메서드를 고치는 이슈도 뺀다 — 한쪽만 잡으면 나중 정착이 남의 설계를 되돌린다.

## 2단계 — 파일 축은 충돌 판정이 아니다

개발이 1개라 충돌은 없다. 연결요소를 뽑는 목적은 둘이다.

| 목적 | 판정 |
|---|---|
| **커밋을 나눌 수 있는가** | 같은 파일이어도 다른 메서드면 hunk 가 갈려 나뉜다. 같은 메서드면 못 나눈다 |
| **순서가 있는가** | 한쪽이 계약(반환 컬럼·응답 키·시그니처)을 정하면 그쪽이 **허브**다. 허브를 먼저 커밋한다 |

```bash
sed -n '/^관련 파일:/,/^---/p' "$f" | grep '^  - '
```

**`관련 파일` 은 증상 위치라 조치 대상과 다를 수 있다.** 이슈 §4 에 조치 파일이 적혀 있으면 그쪽이 우선이고, 조치가 미채택이면 증상 위치로 근사하되 그 근사치임을 표에 밝힌다.

## 3단계 — 합침 판정 (기계가 못 한다)

**같은 파일을 공유하는 쌍마다 "같은 메서드를 고치는가" 를 소스로 확인한다.**

| 판정 | 처리 |
|---|---|
| 다른 메서드 | 커밋을 나눈다. 리뷰·게이트도 따로 |
| **같은 메서드** | **한 커밋으로 묶는다.** 나누면 뒤 커밋이 앞 커밋의 줄을 다시 고쳐서, 앞 커밋만 본 리뷰가 실제로 정착할 코드와 달라진다 |

실측 사례 — `ISS-311`(3계 쓰기를 트랜잭션으로 안 묶는다)과 `ISS-778`(트랜잭션 밖에서 외부 API 를 부른다)은 둘 다 `CoinModel::insertCoin()` 의 **경계 설계**를 바꾼다. 커밋을 나누면 두 번째가 첫 번째 경계를 다시 짜고, 첫 커밋을 통과시킨 리뷰는 존재하지 않는 코드를 본 것이 된다.

**확인이 안 되면 합친다** (fail-safe — 합치면 리뷰 단위가 커질 뿐이고, 가르면 리뷰가 거짓이 된다).

## 4단계 — 배치 표

사용자에게 1회 제시하고 승인받는다. 이후 구성은 바꾸지 않는다.

```
| 순서 | 이슈 | 커밋 단위 | 묶는 파일 | 합침 사유 | 진입 단계 |
```

**진입 단계를 반드시 적는다 — 전부 코드로 가지 않는다.** 이슈 §4 조치 절이 `미채택`·`판단 대기` 면 **성공 기준이 없어** 개발 Agent 에게 줄 것이 없고, 리뷰어는 대조 기준이 없으면 계약대로 `[High] 판정 불가` 로 되돌린다.

| 이슈 §4 상태 | 진입 |
|---|---|
| 계획 문서 `Plan Complete` | 이 커맨드의 개발 Agent 에 포함 |
| 조치 채택, 계획 없음 | `/taskflow:plan` 먼저 — 이번 range 에서 뺀다 |
| **`미채택`·`판단 대기`·판정 불명** | **`/taskflow:analyze` 먼저.** 조치안 선택이 사용자 결정이면 거기서 멈춘다 |

**검증 수단이 없는 이슈도 뺀다.** 근거가 렌더 결과여야 하는데(C3) 그걸 볼 계정·환경이 없으면, 고쳐도 통과 판정을 못 내린다. 그 블로커를 표에 적고 다음 range 로 넘긴다.

### 한 Agent 에 얼마나 담을 수 있나

**성공 기준 합계 10개, 이슈 4건을 넘기지 않는다.** 넘으면 Agent 가 뒤쪽 이슈에서 앞쪽 제약을 잊는다 — 특히 "이 파일의 저 메서드는 건드리지 마라" 류가 먼저 날아간다. 넘치면 range 를 두 번 부른다.

## 5단계 — 실행: 한 Agent 에게 전체를 준다

개발 Agent(`taskflow:step-developer`) **1개**를 띄우고 프롬프트에 다음을 모두 담는다.

- **전체 그림** — 이번 worktree 에서 순서대로 할 이슈 목록과 각자 건드릴 파일. 뒤 이슈가 같은 파일에 들어올 것을 미리 알려야 **상수·메서드 이름을 겹치지 않게** 짓는다
- 이슈마다 — 무엇이 틀렸나 · 변경 · 성공 기준(≤3) · 테스트 범위 · **비목표** · 커밋 메시지
- **커밋 규약** — 이슈마다 `git add <그 이슈 파일> && git commit -m "제목 한 줄"`. 본문·서명 금지
- 공통 제약 — worktree 안에서만 · `tests/unit` + `--filter` 만 · `.env` 금지
- **착수 전 재현** — 이슈마다 결함을 먼저 재현하고 `BASELINE` 에 적는다. **재현이 안 되는 이슈는 건너뛰고 나머지를 진행**한다(요청 자체가 틀렸거나 이미 해소됐을 수 있다)

`composer install` 은 이 Agent 가 처음에 한 번만 한다.

**비목표에 "다른 이슈 소관" 을 명시하라.** 한 Agent 가 전부 보고 있으면 옆 이슈를 같이 고치고 싶어진다 — 그러면 커밋 경계가 무너져 리뷰가 거짓이 된다.

## 6단계 — 검증은 커밋별로

반환되면 커밋마다 `/taskflow:code` 의 검증 절반을 돌린다.

| 입력 | 값 |
|---|---|
| diff | `git show <그 커밋>` — **worktree 전체 diff 가 아니다** |
| 대조 기준 | 그 이슈의 성공 기준·테스트 범위·비목표 |
| BASELINE | 그 이슈 구간의 전·후 |
| 라운드 이력 | 그 커밋의 것만 |

**캡은 커밋마다 독립이다**(리뷰 5·게이트 2). 공유하면 앞 커밋이 다 먹는다.

**리뷰 지적 수정은 새 커밋으로 쌓는다.** 이미 뒤에 다른 이슈 커밋이 있으면 앞 커밋을 고칠 수 없다 — 수정분을 뒤에 붙이고 7단계에서 이슈 단위로 합친다.

슬롯은 단순하다. 개발이 끝난 뒤라 **리뷰어 2인**만 돌고, 커밋들은 순차로 본다.

## 교차 발견 — 한 커밋의 게이트가 다른 축을 깰 때

적대적 검증이 **그 이슈에서 고칠 수 없는 원인**을 찾는 경우가 있다. 실측 사례 — `ISS-200`(엑셀 view)의 게이트 2회차가 깬 것은 view 가 아니라 공용 헬퍼 `mask_name()` 이었다.

| 순서 | 처리 |
|---|---|
| 1 | 그 커밋은 **`BROKEN` 인 채로 멈춘다.** 자기 범위 밖을 고치지 않는다 |
| 2 | 원인 축을 **새 이슈로 등재**한다 (채번 4축 실측 = `issue/README` 대역 표) |
| 3 | 그 이슈를 **이번 range 의 다음 커밋으로** 넣거나, 범위가 크면 별도 range 로 뺀다 |
| 4 | 그것이 들어간 뒤 원 커밋의 **재현물을 재실행**해 재개 |

**2를 건너뛰면 그 발견이 응답 텍스트로만 남고 세션과 함께 사라진다.** 레포 규약이 "대화에만 있는 이슈는 없는 이슈다" 인 이유다.

## 7단계 — 정착

**이슈 하나당 커밋 하나로 정리해서** develop 에 ff 한다. 리뷰 수정분이 뒤에 쌓여 있으면 그 이슈의 커밋과 합친다(`git reset --soft` 후 재커밋 — 공유 브랜치가 아닌 `wip/*` 에서만).

- worktree 가 하나라 **트랙 사이 rebase 가 없다**. 이게 worktree 를 하나로 두는 두 번째 이득이다
- 다만 **develop 이 그 사이 전진했으면 rebase 가 필요하다.** 병렬 세션이 많은 레포에서는 이쪽이 일상이라, 정착 직전 `git log develop` 을 보고 뒤처졌으면 rebase → **전체 테스트 재실행** → 게이트 재현물 재실행
- 수치가 달라지면 정착을 멈추고 보고한다
- 허브가 있으면 **허브 커밋을 앞에 둔다**. 허브가 계약을 정하면 뒤엣것이 그 위에서 갈리지 않는다

## SSOT — 여기서 재정의하지 않는다

| 조각 | SSOT |
|------|------|

## §3 Checkpoint 우선 적용

- 배치 표 승인은 **1회**다. 승인 후 구성을 바꾸려면 다시 올린다
- 정착·머지·push 는 `/taskflow:code` 와 동일하게 §3 을 탄다. 이 커맨드가 우회 통로가 되지 않는다
- 한 이슈가 §3 매칭(비가역·외부 시스템·3파일+ 아키텍처)에 걸리면 **그 커밋만** 멈추고 보고한다. 나머지는 계속 간다

## 이 커맨드가 줄이는 것

**리뷰 비용은 안 준다.** 커밋이 N개면 리뷰도 N벌이고, 그게 루프 비용의 대부분이다.

주는 것은 셋이다 — **worktree·`composer install` 이 1벌**, **본체·Agent 왕복이 이슈마다 생기지 않음**, 그리고 Agent 가 전체 그림을 들고 있어 **이름·계약이 서로 어긋나지 않음**.

그리고 값의 절반은 배치 실수를 막는 데 있다 — 같은 메서드를 다른 커밋으로 가르는 것(리뷰가 거짓이 된다), 남의 세션 파일에 들어가는 것, 정착 후 재검증을 빠뜨리는 것, 교차 발견을 등재 없이 흘리는 것. 넷 다 이 레포에서 실제로 났던 사고다.
