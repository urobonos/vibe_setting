계획 단계 진입 — working/ §분석 완료 후 §계획 섹션을 표준 양식으로 채운다.

## 인자

- `$ARGUMENTS` = (선택) 작업명 kebab-case. 생략 시 가장 최근 working/ 파일 자동 식별.

## 동작 3단계

| 단계 | 동작 | 결과 |
|------|------|------|
| ① working/ 문서 식별 | 인자 매칭 또는 가장 최근 working/ 파일 | 대상 파일 경로 |
| ② §계획 섹션 채움 | 작업 목표 / 수정 대상 표 / Blueprint (디렉토리·시그니처·스키마) / 작업 분해 (WBS) / 실행 계획 | 계획 체크리스트 ≥ 20 채움 (CLAUDE.md §4.3 L132 SSOT) |
| ③ Status 마커 부착 | 시작 라인 또는 파일 끝 `Status: Plan Complete` | 다음 단계 = `/실행` 진입 신호 |

## 자연어 trigger (task-docs 기존 호환)

- `계획 세워줘` / `플랜 작성` / `/plan` (기존 task-docs trigger 호환)

## 강제 hook

| Hook | 검증 | 차단 강도 |
|------|------|----------|
| `doc-template-guard.sh` | unified §계획 헤더 (작업 등급 S/M/L / Blueprint / 수정 대상 / 실행 계획 / WBS) L117~127 | exit 2 (tasks/ 이동 후) |
| `checklist-count-check.sh` | unified 체크리스트 ≥ 30 | exit 2 |

## 종료 마커

```markdown
Status: Plan Complete
```

> `Status: Plan Complete` 부착 시 사용자에게 `/실행` 진입 신호. 부착하지 않으면 `/실행` 진입해도 §계획 미완료 상태로 간주.

## 호출 예


## §3 Checkpoint 우선 적용

§계획 단계의 권고가 다음 조건에 매칭되면 §실행 진입 전 사용자 명시 승인 필수:

| 조건 | 예시 |
|------|------|
| 비가역적 작업 | DB 스키마 변경 / 마이그레이션 실행 / 파일 삭제 |
| 광범위 영향 (3 파일 + 아키텍처) | 모듈 경계 재배치 / 인터페이스 계약 변경 |
| 요구사항 상충 | 성능 vs 가독성 트레이드오프 |
| 외부 시스템 연동 | 외부 API 호출 / 환경변수 변경 |

**worktree 적용 (CLAUDE.md §4.3 (a)):** 본 슬래시 = `working/` 단일 통합 문서 §계획 채움. exemption #5 (`*/.claude/docs/*`) 자동 통과. 단 §실행 진입 시 코드 mutation = worktree 강제.
